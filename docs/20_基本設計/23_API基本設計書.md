# 23_API基本設計書

## 1. 概要

本書は、イベント申込システムのフロントエンドとバックエンドの間で行われるデータのやり取りについて、全APIに共通する仕様と、提供するAPIの一覧を定義する基本設計書である。`docs/10_要件定義/10_要件定義書.md`の各機能を実現するためにどのようなAPIを持たせるかを定める。

個々のAPIの入出力項目・項目とデータベースの対応・エラーは`docs/30_詳細設計/31_API詳細設計書.md`に定める。

- ベースURL：`/api`
- データ形式：リクエスト・レスポンスともにJSON形式とする（CSV出力を除く）。
- 通信方式：HTTPS/HTTPによるREST形式のAPIとする。

### 1.1 自動生成のAPIドキュメントとの役割分担

本システムは、実装から自動生成されるAPIドキュメント（Swagger UI：`/swagger-ui/index.html`、OpenAPI JSON：`/v3/api-docs`）も提供する。

| 資料 | 役割 |
|---|---|
| 本書・`docs/30_詳細設計/31_API詳細設計書.md` | どのAPIを持たせるか、なぜその仕様か（業務上の意図、データの出所）を定める |
| Swagger UI | 実装から自動生成される、常に実装と一致したリファレンス（エンドポイント・型・必須項目）を提供する。動作確認にも使用する |

設計時は本書を基準に実装する。実装後に両者の食い違いが見つかった場合は、どちらが正しいかを確認したうえで、設計書または実装を修正する。

## 2. 共通仕様

### 2.1 認証

- ログイン（AP-010）では、メールアドレスとパスワードを照合して利用者を確認する。
- ログイン後は、ログイン時に確認された利用者を識別する情報を全てのAPIリクエストに付与し、サーバーはこの情報から利用者を特定する。方式と既知の制約は`docs/20_基本設計/24_方式設計書.md`に定める。
- ログイン（AP-010）、利用者登録（AP-011）、稼働確認（AP-900）は、認証情報が無くても呼び出せる。
- 上記以外の全APIは、利用者識別情報が付与されていない場合、対応する利用者が存在しない場合、または退会済みの場合に、認証エラー（401）を返す。

### 2.2 認可

- 各APIを実行できる利用者は「3. API一覧」の認可列に示す。画面を含めた権限の全体像は`docs/20_基本設計/20_機能設計書.md`に定める。
- 管理者専用のAPIに一般利用者からアクセスした場合、権限エラー（403）を返す。
- イベント申込（AP-030）は一般利用者専用であり、管理者からのアクセスは権限エラー（403）とする。
- 本人のデータのみを対象とするAPIで、他人のデータを操作しようとした場合も権限エラー（403）とする。

### 2.3 共通エラーレスポンス

エラー発生時は、以下の形式でレスポンスを返す。

```json
{
  "timestamp": "2026-09-24T17:04:23+09:00",
  "status": 401,
  "error": "Unauthorized",
  "message": "認証が必要です",
  "errors": null
}
```

| フィールド | 型 | 必須 | 内容 |
|---|---|:--:|---|
| timestamp | 日時 | ○ | エラー発生日時 |
| status | 数値 | ○ | HTTPステータスコード |
| error | 文字列 | ○ | HTTPステータスの標準名 |
| message | 文字列 | ○ | 利用者向けメッセージ |
| errors | 配列 | - | 入力値エラーのときのみ、項目ごとのエラー（`{ "field": 項目名, "message": メッセージ }`）。それ以外はnull |

### 2.4 エラー区分とHTTPステータス

| エラー区分 | HTTPステータス | 説明 |
|---|---|---|
| 入力値エラー | 400 | 必須項目の未入力、桁数超過、形式不正等の場合 |
| リクエスト形式エラー | 400 | リクエストの形式が不正で処理できない場合（不正なJSON、パラメータの型不一致等） |
| 業務ルール違反エラー | 400 | 申込締切超過、二重申込、削除不可等、業務ルールに反する場合 |
| 認証エラー | 401 | 利用者を識別できない場合、ログインに失敗した場合 |
| 権限エラー | 403 | 実行権限がない操作を要求した場合 |
| データ未検出エラー | 404 | 指定した対象（イベント・申込・区分・コメント・利用者）が存在しない場合 |
| リクエスト形式エラー（URL・メソッド・本文の形式） | 404・405・415 | 存在しないURLを要求した場合（404）、URLは存在するが対応していないメソッドで要求した場合（405）、本文の形式がJSONでない場合（415） |
| リクエスト過多エラー | 429 | 同一の接続元からの書き込み系リクエストが短時間に集中した場合（2.7） |
| システムエラー | 500 | 想定外の異常が発生した場合 |

個々のエラーのID・発生条件・メッセージは`docs/30_詳細設計/33_共通詳細設計書.md`に定める。

### 2.5 認可と入力値検証の優先順位

管理者専用のAPIおよび一般利用者専用のAPIでは、権限エラーの判定を入力値の検証より先に行う。権限を持たない利用者が不正な内容でリクエストを送った場合、返されるのは権限エラー（403）であり、入力値エラー（400）ではない。

### 2.6 リクエストボディの余剰項目

各APIのリクエストに定義されていない項目がリクエストボディに含まれていても、エラーとはせず無視する。例えば、利用者登録（AP-011）のリクエストボディに利用者区分を含めて送信しても、その値は無視され、登録される利用者区分は常に一般利用者となる。

### 2.7 回数制限

書き込み系API（POST／PUT／DELETE。ログインを含む）は、同一IPアドレスからの直近60秒間のリクエスト数が60回を超えた場合、リクエスト過多エラー（429）を返す。GETは対象外とする。

### 2.8 区分値の返し方

利用者区分・申込状況のように、コードマスタで管理する区分値（`docs/20_基本設計/22_テーブル定義書.md`1.5・7章）は、コードと表示名の両方を返す。

| 区分 | コードのフィールド | 表示名のフィールド | 例 |
|---|---|---|---|
| 利用者区分 | `roleCode` | `roleName` | `"roleCode": 2, "roleName": "管理者"` |
| 申込状況 | `statusCode` | `statusName` | `"statusCode": 1, "statusName": "受付済"` |

- 画面は、表示には表示名を、条件による表示の切り替え（ボタンの表示・非表示等）にはコードを用いる。
- リクエストで区分値を指定する場合は、コードで指定する。

### 2.9 日時の形式

日時は、日本時間の`yyyy-MM-ddTHH:mm:ss`形式の文字列で受け渡す。

### 2.10 パスワードの取り扱い

- パスワードは、ログイン・利用者登録・管理者アカウント登録・パスワード変更のリクエストでのみ受け取り、いずれのレスポンスにも含めない（ハッシュ化した値も返さない）。
- パスワードを含むリクエストの内容は、ログに出力しない。

## 3. API一覧

### 3.1 API IDの採番ルール

API IDは「AP-」＋3桁の番号とし、APIのまとまりごとに10番単位で割り当てる。百の位は利用者の範囲（0：全利用者向け、1：管理者向け、9：システム共通）を表す。APIを追加する場合は、該当するまとまりの空き番号を使用し、既存の番号は変更・再利用しない。

| 番号の範囲 | APIのまとまり |
|---|---|
| 010番台 | 認証・アカウント |
| 020番台 | イベントの閲覧 |
| 030番台 | 申込 |
| 040番台 | お気に入り |
| 050番台 | コメント |
| 120番台 | 管理：イベント・当日受付 |
| 130番台 | 管理：実績・集計 |
| 140番台 | 管理：利用者 |
| 150番台 | 管理：コメント |
| 900番台 | システム共通 |

### 3.3 APIの持たせ方に関する方針

- **一覧系のAPIはページングを行わず全件を返す**。学内利用規模を前提とする（`docs/20_基本設計/24_方式設計書.md`）。
- **イベント一覧の並び替え・絞り込みは画面側で行う**。AP-020は開催日時順の全件を返し、申込数順・お気に入り数順等の並び替えと、キーワード・開催日による絞り込みは、画面が取得済みのデータに対して行う。
- **本人分を扱うAPIは`/api/my/...`とし、対象の利用者をURLやリクエストで指定させない**。対象は認証情報から特定する。管理者が特定の利用者の情報を参照するAPIは`/api/users/{id}/...`として別に設ける。
- **申込実績の一覧とCSVは同じAPI（AP-130）で提供し、パラメータで形式を切り替える**。
- **コメントは1階層の配列で返し、返信の木構造は画面側で組み立てる**。
- **削除済みイベント一覧（AP-123）は、複製（F-120）に必要な項目も返す**。削除済みのイベントはイベント詳細取得（AP-021）で取得できないためである。
