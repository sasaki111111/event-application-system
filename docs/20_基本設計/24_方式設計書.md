# 24_方式設計書

## 1. 概要

本書は、イベント申込システムの全機能に共通する方式（システム構成、認証、入力チェック、エラー処理、ログ、排他制御、セキュリティ、非機能への対応）を定義する基本設計書である。`docs/10_要件定義/10_要件定義書.md`「10. 非機能要件」の要求を、どのような方式で満たすかを定める。

個々のエラー・ログ出力・チェックの一覧と実装方法は`docs/30_詳細設計/33_共通詳細設計書.md`に定める。

## 2. システム構成

### 2.1 構成と技術基盤

利用者のブラウザ上で動作する画面（フロントエンド）が、サーバー（バックエンド）のAPIを呼び出し、サーバーがデータベースを読み書きする3層構成とする。

| 区分 | 採用技術 | 備考 |
|---|---|---|
| フロントエンド | Angular（TypeScript） | 画面の切り替えでページ全体を再読み込みしない構成（SPA）とする |
| バックエンド | Java、Spring Boot | REST形式のAPIを提供する |
| データベース | MySQL 8.0 | 文字コードはUTF-8（utf8mb4） |
| データ交換 | HTTP、JSON | CSV出力のみCSV形式 |
| データベースアクセス | Spring Data JPA | SQLを文字列の連結で組み立てない |
| APIドキュメント | springdoc-openapi（Swagger UI） | 実装から自動生成する |
| 自動テスト | JUnit 5、Mockito、H2（テスト用のインメモリDB） | - |

### 2.2 バックエンドの層構成

バックエンドは次の3層で構成し、層をまたいだ責務の混在を避ける。

| 層 | 責務 | 持たせないもの |
|---|---|---|
| Controller | リクエストの受け取り、認可チェックと入力チェックの起動、レスポンスの整形 | 業務ルールの判定、データベースアクセス |
| Service | 業務ルールの判定、業務上のエラーの発生、トランザクションの制御 | HTTPに関する処理 |
| Repository | データベースの読み書き | 業務ルールの判定 |

複数の機能に共通する処理（認証、権限チェック、エラーの整形、回数制限）は、個々の機能に書かず共通の部品に集約する。

## 3. 認証方式

### 3.1 ログイン時の本人確認

| 項目 | 方式 |
|---|---|
| 本人確認 | メールアドレスとパスワードの照合による |
| パスワードの保存 | BCryptによりハッシュ化した値を`users.password_hash`に保存する。パスワードそのものは保存しない。ハッシュ値から元のパスワードは復元できない |
| パスワードの照合 | 入力されたパスワードと保存済みのハッシュ値を、BCryptの照合機能で比較する |
| パスワードの条件 | 8文字以上72文字以下、英字と数字をそれぞれ1文字以上含む（`docs/10_要件定義/10_要件定義書.md`7章）。上限の72文字は、BCryptが先頭72バイトまでしか照合に用いない制約に対応する。使用できる文字は半角の英字・数字・記号とする |
| メールアドレスの扱い | 前後の空白を除去し、小文字にそろえてから照合・保存する |
| 使用する部品 | Spring Securityのうち暗号化機能（spring-security-crypto）のみを使用する。Spring Securityによる認証の枠組み全体は導入しない |

ログインに失敗した場合（メールアドレスが未登録、パスワードの不一致、退会済み）は、理由によらず同じエラーと同じメッセージを返す（3.5）。

### 3.2 ログイン後の利用者の識別

| 項目 | 方式 |
|---|---|
| 識別方法 | ログイン成功時にサーバーが返した利用者IDを、画面が以降の全APIリクエストのヘッダ（`X-User-Id`）に付与する。サーバーはこの値から利用者を特定する |
| 画面側の保持 | 利用者ID・利用者区分をブラウザの保存領域（`localStorage`）に保持する。ブラウザを再読み込みしてもログイン状態を維持する |
| ログアウト | 画面が保持している利用者ID・利用者区分を消去し、ログイン画面へ遷移する |
| ログイン状態の有効期限 | 設けない |
| 認証を要しないAPI | ログイン、利用者登録、稼働確認 |

**既知の制約**：サーバーは、リクエストに付与された利用者IDをそのまま信用する。そのため、ブラウザの開発者ツールやAPIドキュメント（Swagger UI）から利用者IDを書き換えてAPIを呼び出すと、パスワードを知らなくても他の利用者として操作できる。パスワードによる本人確認は「画面からログインする際」に限って有効である。この制約は、利用範囲を学内に限定する前提（`docs/10_要件定義/10_要件定義書.md`10.1）のもとで許容している。利用範囲を拡大する場合は、サーバーが発行する推測できない値（セッションまたはトークン）による識別へ置き換える必要がある。

### 3.3 パスワードの変更・無効化

| 場面 | 方式 |
|---|---|
| パスワード変更 | 本人が現在のパスワードと新しいパスワードを入力する。現在のパスワードを照合し、一致した場合のみ新しいパスワードのハッシュ値で上書きする。変更後もログイン状態は維持する |
| 退会 | `users.password_hash`をNULLにする。以後、そのアカウントではログインできない |
| パスワードを忘れた場合 | 再設定の機能は提供しない（対象外事項。10章） |

### 3.4 初期データの利用者

運用開始時に用意する利用者（管理者1件、動作確認用の一般利用者）と、その初期パスワードは、初期データ投入用のスクリプト（`backend/src/main/resources/db/seed.sql`）に定める。初期パスワードも3.1の条件を満たすものとし、スクリプトにはハッシュ化済みの値を記載する。

### 3.5 利用者の存在を推測させないための対策

- ログイン失敗時のメッセージは、「メールアドレスが登録されていない」「パスワードが違う」を区別せず、同じ文言とする。
- 利用者登録でメールアドレスが重複した場合のメッセージは、重複の事実を直接伝えず、ログインを案内する文言とする。
- 管理者アカウント登録は管理者のみが利用するため、重複の事実をそのまま伝える。

**限界**：利用者登録が成功するか否かによって、そのメールアドレスが未登録であることは判別できる。メッセージの統一は、文言から登録の有無を断定されることを防ぐ対策である。

## 4. 入力チェック方式

### 4.1 実施場所

| 実施場所 | 目的 | 対象 |
|---|---|---|
| 画面側 | 入力中に誤りへ気づかせる（使いやすさ） | 必須、最大文字数、数値の範囲等、その項目だけで判定できるもの |
| サーバー側 | 不正なデータを登録させない（最終的な保証） | 全ての入力チェック（画面側で行うものを含む）、項目間の関係、データベースの内容との照合、業務ルール |

画面を経由せずAPIを直接呼び出すことができるため、画面側のチェックだけに頼らず、サーバー側で必ず全てのチェックを行う。

### 4.2 チェックの順序

サーバー側では、次の順でチェックを行う。

1. 認証（ログイン済みか）
2. 認可（その操作を行う権限があるか）
3. 単項目チェック（必須、桁数、形式）：違反した項目を全てまとめて返す
4. 項目間・データベースとの照合、業務ルール：最初に見つかった1件を返す

認可を入力チェックより先に行うため、権限のない利用者には入力内容の正否を知らせない。

### 4.3 共通ルール

| ルール | 方針 |
|---|---|
| 前後の空白 | 自動的な除去は行わない。空白のみの入力は未入力として扱う。メールアドレスのみ、前後の空白を除去する |
| 全角・半角 | 変換は行わない |
| 未入力と空文字 | 必須の文字列項目では、未指定・空文字・空白のみを同じ「未入力」として扱う |
| メールアドレス | 前後の空白の除去と小文字化を行ってから、形式チェック・重複チェック・保存を行う |
| 見えない文字 | 制御文字（タブ・改行・復帰を除く）、ゼロ幅文字は、利用者が入力する文字列項目で受け付けない |
| パスワード | 前後の空白を含め、入力された値をそのまま扱う（除去・変換を行わない） |
| 定義されていない項目 | リクエストに含まれていても無視する |

各項目の桁数・形式は`docs/30_詳細設計/30_画面詳細設計書.md`に定める。

## 5. エラー処理方式

### 5.1 エラーの分類とID

エラーを次のとおり分類し、分類ごとの接頭辞と連番でエラーIDを付ける。エラーIDは、設計書・テスト・ログでエラーを一意に指し示すための識別子である。

| 分類 | HTTPステータス | エラーID | 性質 |
|---|---|---|---|
| 入力エラー（リクエスト形式エラーを含む） | 400（存在しないURL・対応していないメソッド・本文の形式の誤りは404・405・415） | `E-V-`＋連番 | 利用者が入力を直せば解消する |
| 業務ルール違反エラー | 400 | `E-B-`＋連番 | 業務上できない操作である |
| データ未検出エラー | 404 | `E-B-`＋連番 | 対象が存在しない |
| 認証エラー | 401 | `E-A-`＋連番 | ログインが必要、またはログインに失敗した |
| 権限エラー | 403 | `E-A-`＋連番 | 権限がない |
| リクエスト過多エラー | 429 | `E-R-`＋連番 | 短時間に操作が集中した |
| システムエラー | 500 | `E-S-`＋連番 | 想定外の異常 |
| 通信エラー | - | （なし） | サーバーに到達できない。画面側で検知する |

エラーIDは追加順の連番とし、欠番は再利用しない。エラーの一覧は`docs/30_詳細設計/33_共通詳細設計書.md`に定める。

### 5.2 サーバー側の方式

- 業務上のエラーは、分類に対応する例外として発生させる。
- 例外からエラーレスポンス（`docs/20_基本設計/23_API基本設計書.md`2.3）への変換は、共通の部品1か所で行う。個々のAPIには例外処理を書かない。
- 想定外の異常が発生した場合は、内部情報（スタックトレース、SQL、クラス名）をレスポンスに含めず、固定のメッセージを返す。詳細はログにのみ出力する。

### 5.3 画面側の方式

- サーバーが返したメッセージがある場合は、それをそのまま表示する。画面側で別の文言に言い換えない。
- 入力エラーは、該当する項目の近くに表示する。該当する項目が画面に無い場合は、画面上部にまとめて表示する。
- サーバーに接続できない場合は、共通のメッセージを表示し、画面が空白にならないようにする。
- 認証エラー（401）が発生した場合は、画面が保持しているログイン状態を解除し、ログイン画面へ遷移する。ただしログインAPIの認証エラー（メールアドレス・パスワードの誤り）は対象外とし、ログイン画面上にメッセージを表示する。

### 5.4 メッセージの作成ルール

- 何ができないのかを具体的に示す。可能な場合は、どうすればよいかも示す。
- 内部情報（SQL、クラス名、テーブル名）を含めない。
- 文末は「〜してください」（入力を促す）、「〜できません」（操作を拒否する）、「〜が見つかりません」（対象が存在しない）のいずれかにそろえる。

## 6. ログ方式

### 6.1 目的

ログは、障害やエラーの原因を調査すること、および**データベースのデータからは後で確認できない事実**を残すことを目的とする。

### 6.2 出力対象の基準

データベースを見れば分かることは、ログに重ねて出力しない。次のいずれかに当たるものを出力する。

| 基準 | 理由 | 例 |
|---|---|---|
| 失敗した操作 | 失敗した操作はデータベースに何も残らない | 入力エラー、権限エラー、業務ルール違反、ログイン失敗、想定外の異常 |
| 実行者がデータベースに残らない操作 | 対象の行に「誰が行ったか」を保持していない | イベントの登録・更新・削除・復元、チェックイン、コメントの削除、管理者アカウント登録、管理者権限の降格、退会 |
| 行が消える、または変更内容が残らない操作 | 操作の事実そのものがデータベースから分からなくなる | コメントの物理削除、パスワード変更 |
| データベースを変更しない操作のうち、記録を残したいもの | データベースに痕跡が残らない | ログイン成功、申込実績のCSV出力 |

次の操作は、データベースから実行者・日時・内容を確認できるため、ログに出力しない。

| 操作 | データベースで確認できる場所 |
|---|---|
| 利用者登録 | `users`の行と`created_at` |
| イベント申込 | `applications`の行（申込者、イベント、状況、`applied_at`） |
| 申込キャンセル・繰り上げ | `applications.status_code`と`updated_at`（キャンセルは本人のみが実行できる） |
| お気に入り登録 | `favorites`の行と`created_at` |
| お気に入り解除 | （履歴として残す必要が無い。`docs/20_基本設計/22_テーブル定義書.md`6章） |
| コメント投稿 | `event_comments`の行（投稿者、`created_at`） |

### 6.3 ログの種類とレベル

| 種類 | レベル | 出力する場面 | 出力する内容 |
|---|---|---|---|
| 操作ログ | INFO | 6.2の基準に当たる操作が成功したとき | 操作の名称、実行した利用者のID、対象のID |
| エラーログ（想定内） | WARN | 入力エラー、業務ルール違反、認証・権限エラー、リクエスト過多 | 実行した利用者のID、API（メソッドとパス）、メッセージ |
| エラーログ（想定外） | ERROR | システムエラー | 上記に加え、エラーID、スタックトレース |
| 調査用 | DEBUG | 開発中の調査 | 本番相当の環境では出力しない |

出力の一覧と書式は`docs/30_詳細設計/33_共通詳細設計書.md`に定める。

### 6.4 出力しない情報

| 情報 | 扱い |
|---|---|
| パスワード（ハッシュ値を含む） | 出力しない |
| メールアドレス、名前等の個人情報 | 出力しない。利用者は利用者IDで示す |
| コメント本文、アンケート回答 | 出力しない |
| リクエストの全文 | 出力しない。必要な項目のみを出力する |
| スタックトレース | 想定外の異常のときのみ出力する |

### 6.5 出力先・保管

出力先はコンソール（標準出力）のみとする。ファイルへの保存、保管期間、監査目的での保持は定めない（10章）。

## 7. トランザクション・排他制御方式

| 項目 | 方式 |
|---|---|
| トランザクションの単位 | 1回のAPI呼び出しにおける業務処理（Serviceの1メソッド）を1トランザクションとする。途中でエラーが発生した場合は、その呼び出しで行った変更を全て取り消す |
| 同時申込・同時キャンセル | 定員の判定から申込の登録・キャンセル待ちの繰り上げまでの間、対象の行を他の処理が変更できないようロックし（悲観ロック）、1件ずつ順に処理する。ロックの対象は、参加区分があるイベントでは対象の区分、無いイベントではイベントとする |
| イベントの編集 | ロックは行わない。管理者による同一イベントの同時編集は想定しない |
| 集計値 | 受付済件数・残り枠等は、申込データから都度算出し、別途保持しない。集計値と申込データの不一致が起きない |

排他制御の対象となる処理と範囲は`docs/30_詳細設計/32_処理詳細設計書.md`に定める。

## 8. セキュリティ対策

| 脅威・観点 | 方針 | 方式 |
|---|---|---|
| 権限のない操作 | 画面側の制御に頼らずサーバー側で拒否する | 全APIで認証・認可を判定する（`docs/20_基本設計/20_機能設計書.md`4章） |
| パスワードの漏えい | パスワードを復元できない形で保存し、どこにも出力しない | 3.1、6.4、`docs/20_基本設計/23_API基本設計書.md`2.10 |
| SQLインジェクション | SQLに入力値を直接連結しない | データベースアクセスの部品（Spring Data JPA）が提供する、値を埋め込む仕組みのみを使用する |
| クロスサイトスクリプティング | 入力値をHTMLとして解釈させない | 画面の表示は、値を自動的に無害化する仕組み（Angularの補間）のみで行う。HTMLとして直接埋め込む機能は使用しない |
| 不正なURLの登録 | 画像URLに実行可能な形式を登録させない | httpまたはhttpsで始まるURLのみを受け付ける |
| CSVを開いたときの数式実行 | 利用者の入力値を数式として解釈させない | 値の先頭が`=`・`+`・`-`・`@`・タブ・復帰のいずれかの場合、先頭に`'`を付けて出力する |
| 総当たり・大量投稿 | 短時間に集中した書き込みを制限する | 同一IPアドレスからの書き込み系APIの呼び出しを、直近60秒間に60回までとする。単一のサーバーで動作する前提の方式であり、サーバーを複数台にする場合は方式の見直しが必要である |
| 内部情報の漏えい | エラー時に内部情報を返さない | 5.2 |
| 利用者の存在の推測 | 登録の有無を断定できる情報を返さない | 3.5 |

## 9. 性能・可用性・保守性

| 項目 | 方針 | 方式 |
|---|---|---|
| 前提とする規模 | 学内の小規模な利用。大規模な同時アクセスは想定しない | - |
| 応答時間・同時アクセス数・稼働率 | 定量目標は定めない | - |
| 一覧の取得 | ページングを行わず全件を返す | 現時点のデータ量では対策不要と判断している |
| 検索・集計の高速化 | 検索・集計に使うカラムにインデックスを設ける | `docs/20_基本設計/22_テーブル定義書.md`8章 |
| 障害時の画面表示 | サーバーに接続できない場合も画面を空白にしない | 5.3 |
| 命名 | クラス名はUpperCamelCase、テーブル・カラム名はsnake_case | `docs/20_基本設計/22_テーブル定義書.md`1.1 |
| 設計書と実装の整合 | 実装から自動生成されるAPIドキュメントと設計書を照合できるようにする | `docs/20_基本設計/23_API基本設計書.md`1.1 |

## 10. 対象外事項

次の事項は、学内利用の規模を前提に、対応方針を定めない。

| 項目 | 理由・補足 |
|---|---|
| ログイン後の利用者識別の強化（セッション・トークン） | 3.2の既知の制約として許容している。利用範囲を拡大する際に検討する |
| パスワードを忘れた場合の再設定 | 利用者へ連絡する手段（メール送信等）を持たないため |
| ログイン状態の有効期限、通信の暗号化方式 | 定めない |
| 応答時間・同時アクセス数・稼働率の定量目標 | 定めない |
| ログのファイル保存・保管期間・監査目的での保持 | 定めない |
| スキーマ変更の管理方法（マイグレーション） | 定めない |
| 稼働環境（サーバー構成、冗長化、バックアップ、CI/CD） | 定めない |
| 一覧取得のページング | 現時点のデータ量では不要と判断している |
