# チーム開発演習 技術仕様書（題材自由・技術要素固定版）

## 0. 位置づけ

- **対象ユニット**：PJ-001〜122（チーム開発演習）。特にPJ-020〜022（要件整理）、PJ-041（担当・期限の設定）、PJ-080（AI駆動スクラッチ開発）、PJ-100〜102（品質・コスト・生産性）と接続する。
- **課題認識**：現行のPJ-020〜022・PJ-080は「チームで自由に決める」ことを重視した構成になっており、技術要素（画面数・API本数・DB構成等）の最低ラインが明記されていない（`11_AIレビュー/02_教育ユニット/07_チーム開発演習.md`でも、PJ-080/081が教材ID分割・進捗管理・評価の基準として粒度が大きすぎる旨が指摘されている）。
- **本書の目的**：業務テーマそのもの（何を作るか）はPJ-020〜022のブレストで各チームが自由に決めるという現行方針を維持したまま、**テーマによらず全チーム共通で満たすべき技術要素の最低ライン**を明文化する。これにより、①発想の自由度を保ちながら、②技術要素の網羅性、③チーム間の規模の公平性、④評価のしやすさ、を担保する。
- **本書が固定しないもの**：業務テーマ（何のシステムを作るか）、画面のUI・レイアウト、チーム独自の拡張機能の内容。
- **本書が固定するもの**：技術スタック、画面数・API数・テーブル数の最低ライン、必須の技術パターン（ロール分岐・CRUD・集計出力等）、テスト・完了条件の基準。

## 1. テーマの決め方（自由・PJ-020〜022と連携）

業務テーマは、PJ-020（作るものの整理）〜PJ-022（機能範囲の整理）の手順に沿って、各チームがブレインストーミングで自由に決定する。ただし、後述の技術要素（2〜4章）を無理なく満たせるよう、テーマ選定時に以下の条件を満たすことを推奨する。

### 1.1 テーマ選定チェック（PJ-020のブレスト時に確認）

- [ ] 「一般ユーザー」と「管理者（承認者・管理担当等）」の、性質が異なる2種類以上の利用者像が自然に存在する業務であるか（PJ-021の利用者像整理と対応）
- [ ] データの登録・参照・更新・削除（CRUD）が一通り発生する業務であるか
- [ ] 何らかの集計・一覧出力（レポート、CSV出力等）が業務として想定できるか
- [ ] 58Dayカリキュラムの残り時間（PJ-080：40.5h）で、画面・API・DBすべてを含めて完成できる規模か

### 1.2 参考テーマ例（あくまでイメージ用・強制ではない）

具体的なイメージが湧きにくい場合の参考として、AP-001でも言及されている通り「図書貸出・経費精算などどんな題材にも応用できる」。例えば以下のようなジャンルが1.1の条件を満たしやすい。

| テーマ例 | 一般ユーザー | 管理者側 | 業務エンティティ例 |
|---|---|---|---|
| 経費精算システム | 経費を申請する社員 | 承認する上長・経理担当 | 経費申請、申請明細 |
| 図書貸出システム | 本を借りる利用者 | 蔵書を管理する司書 | 蔵書、貸出記録 |
| 社内イベント申込システム | イベントに申し込む社員 | 定員・出欠を管理する運営担当 | イベント、参加申込 |
| 社内問い合わせ管理システム | 問い合わせを起票する社員 | 対応する情報システム担当 | 問い合わせ、対応履歴 |

いずれのテーマを選んでも、2〜4章の技術要素の最低ラインは共通で適用する。

## 3. 画面設計（UI）— 最低5画面（テーマ非依存の型）

テーマは自由だが、画面は以下5種類の「型」を最低ラインとして満たすこと。画面名・具体的な項目はチームがテーマに合わせて決定する。

### 3.1 必須の画面の型

| 画面ID | 画面の型 | 主な利用者 | 必須要件 |
|---|---|---|---|
| SC-01 | ログイン画面 | 全ユーザー | SSO入口（ダミー） |
| SC-02 | 一覧・申請/登録画面 | 一般ユーザー | 対象データの一覧表示＋新規登録（CRUD：作成・参照） |
| SC-03 | 自分の登録データ確認・取消画面 | 一般ユーザー | 自分が登録したデータの一覧＋更新または取消（CRUD：更新・削除のいずれか） |
| SC-04 | マスタ・承認管理画面 | 管理者 | 管理対象データの登録・編集・削除（CRUD全操作） |
| SC-05 | 実績・集計出力画面 | 管理者 | 集計結果のCSV等での出力 |

![SC-01のログインを起点に、一般ユーザー系の一覧・登録画面と自分のデータ確認画面、管理者系のマスタ管理画面と実績出力画面へ分岐する画面遷移関係図](../04_教材/08_チーム開発演習/images/PJ-05_02_画面遷移関係図.png)

### 3.2 最低5画面とする理由

チーム間で規模を揃えつつ、以下の技術要素を最低1回は必ず通しで経験させるための最小構成が5画面である。

- **ロール分岐**：一般ユーザー向け（SC-02, 03）と管理者向け（SC-04, 05）を両方含む（IT-163 認証と認可、AP-022の権限設計と接続）
- **CRUD全操作**：作成・参照・更新・削除のすべてを、5画面のどこかで必ず経験する
- **異なる技術ジャンル**：通常の一覧・登録操作（SC-02〜04）に加え、集計・出力系の技術要素（SC-05、AP-140バッチ処理との接続）を1つ含める

### 3.2' SPA要件（画面遷移の実装方式）

「Angularで画面を作る」だけでは、画面ごとに別々のページ（フルリロードを伴う遷移）を作っても要件を満たせてしまう。SPAとして成立させるため、以下を必須とする。

- SC-01〜05（＋チーム独自画面）は1つのAngularプロジェクト内の別コンポーネントとして実装する
- 画面間の遷移はAngular Router（`app.routes.ts`のルート定義、`routerLink`／`Router.navigate()`）によるクライアントサイド遷移とし、ページ全体の再読み込みを発生させない
- `<a href="...">`によるサーバー遷移、画面ごとに別々のAngularアプリを起動する実装は不可
- 実装前に、AP-002の考え方で画面遷移図を作成し、各画面のルートパス・コンポーネント対応を決めてから着手する

### 3.3 テーマへの当てはめ例（経費精算システムの場合）

上記の型が、テーマによってどう具体化されるかのイメージ例。

| 画面ID | 型 | 経費精算システムの場合 |
|---|---|---|
| SC-01 | ログイン | ログイン画面 |
| SC-02 | 一覧・申請/登録 | 経費申請画面（申請一覧＋新規申請） |
| SC-03 | 自分のデータ確認・取消 | 申請状況確認画面（自分の申請一覧＋取り下げ） |
| SC-04 | マスタ・承認管理 | 承認画面（上長が申請を承認／却下） |
| SC-05 | 実績・集計出力 | 経費実績出力画面（経理担当がCSV出力） |

### 3.4 任意拡張画面（チーム独自）

PJ-020のブレストで採用した独自機能に応じて、SC-06以降を自由に追加する（1〜2画面が目安）。

**画面数の目安：最低5画面（必須）／標準6〜7画面／上限は目安なし（ただしPJ-041のWBSで実現可能性を確認）**

## 4. 内部設計（バックエンド・DB）— テーマ非依存の最低ライン

### 4.1 アーキテクチャ構成

```text
[Angular] Component → Service（HttpClient） → Spring Boot REST API
                                                    ↓
                                    [Controller] → [Service] → [Repository]
                                                    ↓
                                                 [MySQL]
```

![Angular・Spring Boot・MySQLの3層構成と、Controller・Service・Repositoryの役割分担を示すアーキテクチャ構成図](../04_教材/08_チーム開発演習/images/PJ-05_03_3層アーキテクチャ構成図.png)

- Controller：リクエスト受付・レスポンス返却のみ（業務ロジックを書かない）
- Service：業務ロジック（上限チェック・状態チェック等）、業務例外のスロー
- Repository：DBとの読み書きのみ
- 共通エラーハンドリング：`@ControllerAdvice`で業務例外→ステータスコード変換（AP-021設計に準拠）

### 4.2 APIエンドポイント一覧（最低ライン・8本、テーマ非依存の型）

| No | メソッド | エンドポイントの型（例） | 概要 | 権限 |
|---|---|---|---|---|
| 1 | GET | /api/{対象データ} | 対象データの一覧取得 | 一般以上 |
| 2 | POST | /api/{対象データ} | 新規登録・申請 | 一般以上 |
| 3 | GET | /api/{自分の登録データ} | 自分の登録データ一覧取得 | 一般以上（本人分のみ） |
| 4 | PUT または DELETE | /api/{自分の登録データ}/{id} | 更新または取消 | 一般以上（本人のみ） |
| 5 | POST | /api/{管理対象マスタ} | 管理者によるマスタ登録 | 管理者のみ |
| 6 | PUT | /api/{管理対象マスタ}/{id} | 管理者によるマスタ編集 | 管理者のみ |
| 7 | GET | /api/reports/{対象データ} | 実績・集計のCSV等出力 | 管理者のみ |
| 8 | GET | /api/{対象データ}/{id} | 対象データの詳細取得 | 一般以上 |

チーム独自機能を追加する場合、上記に加えてAPIを設計する（AP-020のエンドポイント設計手順に従う）。

### 4.3 DBテーブル設計（最低ライン・3テーブル＋拡張分、テーマ非依存の型）

| テーブルの型 | 役割 | 必須カラム | 備考 |
|---|---|---|---|
| `users` | 利用者 | id, name, email(UNIQUE), role | role: `general`/`admin`など2種類以上の権限区分 |
| 業務エンティティ1（例：申請、貸出記録、参加申込等） | 一般ユーザーが登録する業務データ | id, user_id(FK), 対象を表す外部キー, status, created_at, updated_at | statusで状態管理（例：申請中／承認済み／却下等） |
| 業務エンティティ2（例：マスタとなる対象。経費科目、蔵書、イベント等） | 管理者が管理する対象データ | id, name, 数量/上限等の管理値 | 業務エンティティ1から外部キーで参照される |

- チーム独自機能を追加する場合、原則1テーブル以上を追加する（正規化を崩さない範囲で）
- 監査カラム（created_at/updated_at）は全テーブル必須（DV-060〜065、AP-060の制約設計に準拠）

### 4.4 必須の業務ロジック（最低2件、テーマ非依存の型）

| ロジックの型 | 内容の例 | 違反時の挙動 |
|---|---|---|
| 上限・妥当性チェック | 数量・金額・定員などが許容範囲を超えないこと（例：予算上限、定員上限、在庫数） | 400エラーで理由を返す |
| 日付・状態チェック | 日付の妥当性（過去日不可等）、または状態遷移の妥当性（例：承認済みのデータは編集不可） | 400エラーで理由を返す |

具体的な内容はテーマに合わせてチームがAP-040〜042の手順で設計する。

## 5. チーム体制・役割分担の目安（PJ-001〜003、PJ-041と接続）

標準チーム規模を4〜6名と想定し、画面5＋API8＋テーブル3の規模から逆算した役割配分の目安は以下の通り（PJ-041の担当・期限設定時の参考値）。

| 役割 | 人数目安 | 主担当 |
|---|---|---|
| フロントエンド担当 | 1〜2名 | SC-01〜05のAngular実装 |
| バックエンド担当 | 2名 | Controller/Service/Repository実装（API 1〜8） |
| DB／設計担当 | 1名 | テーブル設計・ER図、Repository層のSQLレビュー |
| PM／QA（レビュー・進捗・テスト統括） | 1名 | PJ-042進捗管理、PM-040〜041レビュー、TQ系テスト統括 |

- 4名チームの場合は「DB担当」を「バックエンド担当」と兼務、「PM/QA」を「フロントエンド担当」と兼務する等、PJ-003の責任範囲表で明確化する。
- 依存関係（DV-108）：DB設計→API実装→画面実装の順に着手できるよう、PJ-041のWBSでは最初にDB・API設計を完了させる工程を優先する。

## 付録：本書と既存教材の対応関係

- 3〜4章の「画面・APIエンドポイント・テーブルの型」は、AP-001（画面一覧）・AP-020（API設計）・AP-060（テーブル設計）で個人演習として扱った「社内備品予約システム」の構造（一般ユーザー向け機能／管理者向け機能／集計出力）を一般化したものである。同じ型を、今度はチームで、自分たちが選んだ別テーマに当てはめて設計・実装させることで、「型の理解を新しい題材に応用する」という学習効果を狙う。

- 5章の役割配分は、PJ-001（役割分担）・PJ-002（開発体制）・PJ-041（担当・期限の設定）で各チームが検討する際の参考値であり、強制ではない。
