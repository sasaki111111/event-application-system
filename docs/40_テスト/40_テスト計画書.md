# 40_テスト計画書

## 1. 概要

本書は、イベント申込システムのテストについて、テストレベルの区分、テストケースの書き方、テスト環境、テストデータ、合否の基準、証跡の残し方を定めるテスト計画書である。個々のテストケースは、テストレベルごとのテスト仕様書に定める。

| 資料 | 内容 |
|---|---|
| 本書 | テスト全体の方針・ルール |
| `docs/40_テスト/41_単体テスト仕様書.md` | 単体テスト（UT）のテストケース |
| `docs/40_テスト/42_結合テスト仕様書.md` | 結合テスト（IT）のテストケース |
| `docs/40_テスト/43_総合テスト仕様書.md` | 総合テスト（ST）のテストケース |
| `docs/40_テスト/44_テスト結果表.xlsx` | テストケースごとの実施結果の記録（結果、実施日、実施者、実際の結果、証跡） |

テストは設計書に定めた仕様を確かめるものであり、期待結果は設計書の記載を根拠とする。テスト仕様書に独自の仕様は定めない。設計書とテスト仕様書が食い違う場合は、設計書を正としてテスト仕様書を見直す。

## 2. テストレベル

| レベル | 目的 | 確認する範囲 | 根拠とする設計書 | 実施方法 |
|---|---|---|---|---|
| 単体テスト（UT） | 1つの部品が、単独で正しく動くことを確認する | バックエンドのService層の業務ロジック（Repositoryは模擬のものに置き換える）。フロントエンドの部品（画面の処理、共通の関数） | `32_処理詳細設計書`（業務ルール・条件分岐）、`30_画面詳細設計書` | 自動テスト |
| 結合テスト（IT） | 部品をつないだ状態で、機能ごとに正しく動き、データベースが正しく更新されることを確認する | API結合：Controller〜Service〜Repository〜データベース。画面結合：画面〜API〜データベース | `31_API詳細設計書`、`30_画面詳細設計書`、`33_共通詳細設計書`、`22_テーブル定義書` | API結合は自動テストと手動（Swagger UI）。画面結合は手動（ブラウザ） |
| 総合テスト（ST） | 業務の流れに沿って、複数の機能・複数の利用者をまたいで正しく動くこと、および非機能の要求を満たすことを確認する | 業務シナリオ（`10_要件定義書`の業務フロー）。複数利用者の操作、同時申込、非機能（排他制御、回数制限、セキュリティ、障害時の表示） | `10_要件定義書`、`24_方式設計書` | 手動（ブラウザ）。一部は自動テスト |

- 1つの機能について、データベースの更新結果まで確かめるテストは結合テストに置く。総合テストは、結合テストで確認済みの機能を組み合わせた流れを確かめる。
- 各レベルは、下位のレベルが完了してから実施する（UT → IT → ST）。

## 3. テストケースの書き方

### 3.1 基本のルール

1. **正常系と異常系を分ける。** テスト仕様書では、対象（機能・API・画面）ごとに「正常系」と「異常系」を別の表にする。
   - 正常系：仕様どおりの入力・状態で、処理が成功することを確認するケース。
   - 異常系：入力の誤り、業務ルール違反、権限なし、対象なし等で、定められたエラーになり、データが変更されないことを確認するケース。
2. **1つのテストケースには、1つの条件と1つの期待結果だけを書く。** 複数の条件や複数の結果を1ケースにまとめない。
   - 誤った例：「名前が100文字なら201、101文字なら400」
   - 正しい例：正常系「名前が100文字 → 201」と、異常系「名前が101文字 → 400」の2ケースに分ける。
3. **境界値は、通る側と拒否される側を別のケースにする。** 上限ちょうど（通る）は正常系、上限を1つ超えた値（拒否される）は異常系に置く。
4. **権限は、利用者区分ごと・APIごとに別のケースにする。** 「管理者専用のAPIすべてを一般利用者で呼ぶ」のように束ねない。
5. **期待結果は、確認できる事実で書く。** 「正しく動く」「問題ない」とは書かない。
6. **「条件」とは、入力・前提・操作する人の違いを指す。** 1つの条件に対する結果を、複数の箇所（応答のステータス、応答の項目、データベースの状態、画面の表示）で確かめる場合は、1つのテストケースにまとめる。確かめる箇所ごとにケースを分けることはしない。
7. **自動テストも、1つのテスト（メソッド）で1つの条件だけを確かめる。** テスト仕様書のテストケースと自動テストは1対1で対応させ、テストの実行結果から、どのテストケースが合格したかを判別できるようにする。

### 3.2 期待結果に書くこと

| テストの種類 | 期待結果に書くこと |
|---|---|
| 単体テスト | 戻り値、発生する例外とメッセージ、模擬のRepositoryに対する呼び出し |
| API結合テスト | HTTPステータス、レスポンスの項目、**データベースの状態**（どのテーブルのどのカラムがどうなるか。異常系では「変更されない」こと） |
| 画面結合テスト | 画面の表示・遷移、**データベースの状態** |
| 総合テスト | 各ステップの画面の表示、シナリオの節目でのデータベースの状態 |

エラーのケースでは、HTTPステータスとメッセージの両方を期待結果とする。エラーIDは`33_共通詳細設計書`3章のものを用いる。

### 3.3 根拠

各テストケースには、期待結果の根拠となる設計書の箇所を、ID（機能ID `F-`、画面ID `SC-`、API ID `AP-`、業務ルールID `R-`、チェックID `C-`、エラーID `E-`）または資料名と章番号で示す。

## 4. テストIDの体系

| レベル | 形式 | 例 | 説明 |
|---|---|---|---|
| UT | `UT-{対象}-{N/E}{連番2桁}` | `UT-APP-N01`、`UT-APP-E01` | 対象はテスト対象のクラス等の略称。Nは正常系、Eは異常系 |
| IT（API結合） | `IT-{API ID}-{N/E}{連番2桁}` | `IT-AP030-N01` | API IDは`23_API基本設計書`のID（ハイフンを除く） |
| IT（画面結合） | `IT-{画面ID}-{N/E}{連番2桁}` | `IT-SC020-N01` | 画面IDは`21_画面基本設計書`のID（ハイフンを除く） |
| IT（API結合の共通） | `IT-CMN-{N/E}{連番2桁}` | `IT-CMN-E01` | 認証・リクエスト形式等、全APIに共通する確認 |
| IT（画面結合の共通） | `IT-NAV-{N/E}{連番2桁}` | `IT-NAV-E01` | ログイン状態と画面遷移の制御等、全画面に共通する確認 |
| ST（業務シナリオ） | `ST-{シナリオ番号2桁}-{ステップ2桁}` | `ST-01-03` | シナリオ番号は、正常系シナリオを01から、異常系シナリオを11から付ける。ステップ番号は実施する順 |
| ST（非機能） | `ST-NF-{N/E}{連番2桁}` | `ST-NF-N01` | 非機能の確認。Nは正常系、Eは異常系 |

テストケースを追加する場合は、末尾の番号を使用する。既存の番号は変更・再利用しない。

## 5. テスト環境

| 区分 | 自動テスト（UT、ITの一部） | 手動テスト（IT、ST） |
|---|---|---|
| バックエンド | `mvnw test` | `mvnw spring-boot:run -Dspring-boot.run.profiles=local`（`http://localhost:8080`） |
| データベース | H2（インメモリ、MySQL互換モード）。テストごとに初期化する | MySQL 8.0（`eventapp`）。`schema.sql`→`seed.sql`を投入した状態から開始する |
| フロントエンド | `npm test` | `npm start`（`http://localhost:4200`） |
| ブラウザ | - | Google Chrome。開発者ツールのNetworkタブでAPIの通信を確認できること |
| APIの実行 | - | Swagger UI（`http://localhost:8080/swagger-ui.html`） |
| データベースの確認 | - | MySQLのクライアント（MySQL Workbench等）でSELECT文を実行する |

## 6. テストデータ

手動テストは、`schema.sql`→`seed.sql`の投入直後の状態に、次のデータを追加して開始する。TD-01〜TD-03とTD-05は画面から登録する。TD-04は画面から作れないため、SQLで用意する。

| ID | 内容 | 用意の方法 |
|---|---|---|
| TD-00 | 初期データ。利用者3件（ID=1 一般ユーザー `general@example.com`、ID=2 管理者 `admin@example.com`、ID=3 退会確認用ユーザー `withdraw-test@example.com`。パスワードはいずれも`Test1234`）、イベント51件、コードマスタ（利用者区分2件、申込状況3件） | `seed.sql` |
| TD-01 | 参加区分付きのイベント「区分テスト」：区分「一般」定員1・「学生」定員1、アンケート文言「参加の目的を教えてください」、申込締切・開催日時は未来 | SC-121で登録 |
| TD-02 | 定員1のイベント「定員1テスト」（区分なし、アンケートなし）、申込締切・開催日時は未来 | SC-121で登録 |
| TD-03 | 申込締切が過去、開催日時が未来のイベント「締切済テスト」 | SC-121で登録（申込締切には過去の日時を入力できる） |
| TD-04 | 開催日時が過去のイベント「開催済テスト」と、一般ユーザー（ID=1）の受付済の申込1件 | TD-02と同様に登録して申し込んだ後、`UPDATE events SET start_at = NOW() - INTERVAL 1 DAY, application_deadline = NOW() - INTERVAL 2 DAY WHERE name = '開催済テスト';` |
| TD-05 | 2人目の一般利用者「一般ユーザー2」`general2@example.com`（パスワード`Test1234`） | SC-010の新規登録 |

- テストでデータを変更した後に別のテストを行う場合は、前提となる状態を各テストケースの「前提」に従って作り直す。状態が分からなくなった場合は、`schema.sql`→`seed.sql`を流し直してTD-01〜TD-05を再度用意する。
- 区分値はコードで保存される。SQLで確認・更新する場合は、申込状況コード（1：受付済、2：キャンセル待ち、9：キャンセル済）、利用者区分コード（1：一般利用者、2：管理者）を用いる（`22_テーブル定義書`7章）。

## 7. 合否の判定

- テストケースの「期待結果」（データベースの状態を含む）をすべて満たした場合を合格（OK）、1つでも満たさない場合を不合格（NG）とする。
- 前提を作れない、判断できない場合は保留とし、理由を記録する。
- 自動テストは、テストの実行結果が成功であることをもって合格とする。

## 8. 証跡

テストを実施したことと、その結果を後から確認できるよう、次の証跡を残す。

| テストの種類 | 残す証跡 | 証跡に含めること |
|---|---|---|
| 自動テスト | テストケースごとの結果一覧（テストID・結果・テスト名を1行ずつ並べたテキスト）と、その元になるテスト実行レポート（Surefireの出力、`npm test`の出力） | 実行日時、実行コマンド、テストケースごとの成否、元にした実行レポートのファイル名 |
| API結合テスト（手動） | Swagger UIの実行結果の画面 | リクエストのURL・ヘッダ・本文、レスポンスのステータスと本文、レスポンスの日時 |
| 画面結合テスト・総合テスト | ブラウザの画面 | **アドレスバー（URL）と、日時が分かるもの（OSの時計等）を含める。** 画面の一部だけを切り取らない |
| データベースの状態 | SELECT文とその実行結果 | 実行したSELECT文、結果の行、実行日時。更新を確認する場合は、操作の前と後の両方を残す |

- 証跡のファイル名は、テストIDで始める（例：`IT-AP030-N01.png`、`IT-AP030-N01_db.txt`）。1つのテストケースに複数の証跡がある場合は、末尾に連番を付ける。
- 自動テストは、1回の実行で多数のテストケースを確認するため、テストケースごとのファイルは作らない。テストレベルごとの結果一覧（例：`UT_バックエンド_結果一覧_20261007.txt`）を証跡とし、テスト結果表の証跡欄にはそのファイル名を記入する。結果一覧は実行レポートから作成し、元の実行レポートも同じフォルダに保存する。
- 証跡は`docs/40_テスト/evidence/`に、テストレベルごとのフォルダ（`UT`・`IT`・`ST`）に分けて保存する。
- テスト結果表には、テストケースごとに、実施日、実施者、結果（OK／NG／保留）、実際の結果（期待結果と異なる場合はその内容）、証跡のファイル名を記録する。
- 設計書に掲載している画面イメージ（`docs/20_基本設計/images/`）は設計上の図であり、証跡には用いない。

## 9. 不具合の管理

1. 不合格（NG）になったテストケースは、GitHubのIssueとして起票する。タイトルは「[BUG] テストID 事象の要約」とし、再現手順、期待結果、実際の結果、発生した環境を記載する。
2. 修正は作業ブランチで行い、プルリクエストに対応するIssueとテストIDを記載する。
3. 修正の取り込み後、不合格になったテストケースを再実施する。同じ機能の他のテストケースも再実施する。
4. 修正内容が自動テストで確認できる場合は、再発を防ぐため、対応する自動テストを追加する。
5. 再テストの結果は、最初の結果を消さずに、テスト結果表に追記する。

## 10. 完了の条件

- すべてのテストケースが実施済みで、結果が合格であること（保留のケースは、理由と対応方針が記録されていること）。
- 不合格になったテストケースに対応するIssueが、すべてクローズされていること。
- 各テストケースの証跡が、8章のとおりに残されていること。
