## 1. システム全体構造

```
利用者（ブラウザ）
  ↓ 画面表示・操作
Frontend（Angular SPA、http://localhost:4200）
  - Component（*.ts + *.html）：画面の表示状態と操作ハンドラ
  - core/*-api.ts：backend APIの薄いラッパー（HttpClient）
  - dummyAuthInterceptor：全リクエストにX-User-Idヘッダを自動付与
  - httpErrorInterceptor：通信不可時のメッセージを正規化
  - authGuard / adminGuard：ルート単位のアクセス制御
  ↓ HTTP（JSON、X-User-Idヘッダ付き）／REST API（/api/**）
Backend（Spring Boot、http://localhost:8080）
  - AuthInterceptor：X-User-Idヘッダからログイン利用者を解決（関所）
  - Controller：HTTPリクエストの受付、権限チェック（管理者/一般の判定）
  - Service：業務ロジック（締切判定・定員判定・キャンセル待ち・繰り上げ・権限判定等）
  - Repository（Spring Data JPA）：DBへの問い合わせ（メソッド名からクエリ自動生成＋悲観ロック用@Query 3箇所）
  - Entity：DBの1行を表すJavaクラス（一部は業務ロジックも保持：isOpen()等）
  - GlobalExceptionHandler：例外を統一JSON形式に変換
  ↓ JDBC（Hibernate/JPA経由）
MySQL（eventappデータベース、ddl-auto: none＝スキーマは手動適用）
  - users / events / ticket_types / applications / favorites / event_comments
  ↑ SELECT結果 / INSERT・UPDATE結果
Backend（Entity→DTO変換）
  ↑ HTTPレスポンス（JSON、成功時2xx／エラー時4xx＋ErrorResponse形式）
Frontend（画面へ反映、エラーはerr.error?.messageを表示）
  ↑ 画面表示
利用者（ブラウザ）
```

3層構成であり、要件定義書§2.3の図（利用者→フロントエンド→バックエンドAPI→データベース）と実装のレイヤー構成（Component/Api Service → Controller/Service/Repository → MySQL）は一致していることを確認した。認証はパスワードを使わず、ログイン時に確認した利用者IDを`X-User-Id`ヘッダで以降の全リクエストに付与する方式（要件定義書§10.1）であり、`dummyAuthInterceptor`（フロント）と`AuthInterceptor`（バック）がこの往復を実現している。

## 7. 結論

- `docs/01_要件定義書.md`の全15機能（F-01〜F-15）について、対応する画面・API・Controller・Service・Repository・Entity・DBテーブルを実際のソースコードで特定し、追跡できることを確認した。
- 全25 API・全14画面・全6テーブルについて、設計書との内容一致をコード読解で確認した。うち大半（21/25 API）は自動テスト（67件、本セッションで実行し全件成功）で裏付けが取れており、さらにユーザーが起動した実MySQLにbackendを接続してのcurl疎通確認により、残りのAP-06・AP-10・AP-11・AP-15を含む計25/25 APIについて実データでの動作を確認した。検証用に作成したイベント・申込・お気に入り・コメントは確認後すべて後始末し、既存データへの影響は無い。
- 設計と実装の間に機能的な不一致（分類A・B）は見つからなかった。軽微な記録事項として発見した「コードコメント・一部テストメソッド名の旧API番号表記」と「未使用Repositoryメソッド1件」は、ユーザー確認のうえ本セッション内で対応済み（前者は全箇所を現行のAP-XX番号へ統一、後者は削除）。修正後も`mvn test`67件が全て成功することを確認している。
- 残る未確認範囲は、Angular画面を実際にブラウザで操作しての最終確認（ボタンクリック・カレンダー表示・確認ダイアログの見た目等）のみであり、本セッションにはブラウザ操作ツールが無いため実施できていない（[07-06_問題・確認事項.md](07-06_問題・確認事項.md)No.3）。なお実DB調査の過程で、チェックイン・再チェックイン確認ダイアログ・CSV除外・管理者アカウント登録については、本セッション以前に既に何らかの形で動作確認が行われていた形跡（削除済みテストイベント・複数の管理者アカウント）が見つかっている。
- 本書と6件の補助資料をあわせて参照すれば、「利用者がどのボタンを押すと、どの画面のどのコードが動いて、どのAPIが呼ばれて、Backendのどのクラスを通って、どのDB・テーブルにアクセスして、その結果がどう画面に戻ってくるのか」を一貫して追跡できる状態になっている。
