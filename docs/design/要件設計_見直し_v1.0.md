# 要件設計 見直し（現状分析・追加提案）

作成：2026-09-18 ／ v1.0

## 0. 目的・参照資料

アジャイル開発フェーズのWBSを作る前に、「現状のシステムが技術仕様書・成果発表実施要領の要求をどこまで満たしているか」を棚卸しし、不足・推奨・任意の3段階で整理する。この整理をもとに、次のWBSのバックログ・工数配分を組み直す。

参照：
- `docs/design/要件定義書_v1.0.md`（v1.7）
- `docs/08_チーム開発演習_技術仕様書_v0.1.md`
- `docs/09_チーム開発演習_成果発表実施要領_v0.1.md`

判定区分は以下の意味で使う。

| 区分 | 意味 |
|---|---|
| **必須** | 技術仕様書・実施要領が完了条件として明記している。未達なら発表前に対応が要る |
| **推奨** | 明記された必須要件ではないが、評価観点・完成度の観点から対応した方がよい |
| **任意** | やると加点的だが、優先度は低い。時間が余れば |

## 1. 現在のアプリの状況（サマリー）

一般ユーザーがイベントを検索・申込し、管理者がイベントの登録・編集・削除と申込実績の確認を行うWebアプリケーション。技術仕様書の必須ライン（5画面・API8本・3テーブル）を満たした上で、以下の機能追加を実装済み。

- ログイン方式変更（メールアドレス）＋軽い会員登録
- イベント検索（キーワード・開催日範囲）
- 管理者ダッシュボード
- 管理者ユーザー一覧（マスタ確認用）
- キャンセル待ち・自動繰り上げ
- イベントのソフトデリート・復元

テスト：バックエンドのユニットテスト（`ApplicationServiceTest`12件・`EventServiceTest`7件）、結合テスト（`ApiIntegrationTest`、API-01〜06を実DB相当のH2で検証）、STシナリオ2本（`G-3_STシナリオ.md`）、バグチケット1件（`G-4_バグチケット.md`）。

ドキュメント：要件定義書・API設計書・テーブル定義書・画面遷移図・詳細設計書（基本設計〜詳細設計一式）、コードベース解説・アーキテクチャ構成図（補助資料）、動作確認チェックリスト・振り返り。

- **必須（対応要）**：Git運用の実績作り。今からでも、新規アジャイルフェーズの各バックログ項目を`feature/xxx`ブランチで実装し、PRを作成してからmainにマージする運用に切り替える（完了条件「すべての実装がPRレビューを経てmainにマージされている」に直接対応）。過去分を遡ってやり直す必要はなく、**ここから先を正しい運用にする**方針でよい。

## 6. docsの棚卸し・不足しているもの

### 揃っているもの

要件定義書・API設計書・テーブル定義書・画面遷移図・詳細設計書（基本設計〜詳細設計）、D-8/F-1/F-2/G-3/G-4（動作確認・テスト記録）、コードベース解説・アーキテクチャ構成図（補助資料）、動作確認チェックリスト、振り返り、README（セットアップ手順）。

### 不足しているもの

| ドキュメント | 区分 | 理由 |
|---|---|---|
| Git運用の実績記録（Issue一覧・PR一覧・レビュー記録） | 必須相当 | §2の指摘に対応。実際に運用を始めたら、その証跡（PRリンク等）を残す場所が必要 |
| 新機能分のAPI結合テスト・STシナリオ | 推奨 | §4・§5の指摘に対応。既存の`ApiIntegrationTest`・`G-3_STシナリオ.md`に追記する形で対応可能（新規ファイル不要） |
| 非機能要件の明文化（性能・可用性等） | 任意 | 現状は「教材段階のため考慮しない」という前提が要件定義書・テーブル定義書に散在しているが、1箇所にまとまった非機能要件の章は無い |
| 用語集 | 任意 | 「受付済／キャンセル待ち／キャンセル済」等の用語は各設計書に分散している。演習の規模では無くても支障は無い |

## 7. 総括：次にWBSを作る前に決めておくこと

1. **Git運用をどう扱うか**：新規アジャイルフェーズから`feature/xxx`ブランチ＋PRの運用を実際に始めるかどうか。始める場合、WBSの各タスクに「ブランチ作成」「PR作成」の工数を乗せる必要がある。
2. **404ページを追加するか**：小規模（1h未満）なので、必須化してもコストは低い。
3. **新機能の結合テスト・STシナリオ拡充をどこまでやるか**：新規バックログの機能追加と合わせてやるのか、別枠で先に片付けるのか。
4. **非機能要件・用語集を作るか**：任意なので、時間に余裕があれば。

これらの決定を踏まえて、新規アジャイルフェーズのWBS（工数配分・バックログ）を組み直すことを推奨する。
