# イベント申込システム 要件定義（確定版）

v2.0（2026-09-18）

チーム開発演習（1人・教材作成テスト段階）／08_チーム開発演習_技術仕様書 v0.1 準拠。
以後の設計（API設計書・テーブル定義書・詳細設計書・画面遷移図）はすべて本書を根拠とする。

---

## 1. システム概要

- **システム名**：イベント申込システム
- **目的**：一般ユーザーはサークル・イベント運営者が企画したイベント（ボードゲーム会・スポーツ大会・ライブ・撮影会など）を、一覧・検索・カレンダーで確認して申し込み、自分の申込状況（受付済／キャンセル待ち／キャンセル済、キャンセル待ちの場合は順位も）を確認・取消できる。気になるイベントはお気に入り登録しておき、開催前後を問わずイベントページでコメントを通じて他の参加者と交流できる。管理者はイベントの登録・編集・削除を行い、主催者名・画像・参加区分（定員を分けた枠）・申込時アンケートを設定でき、当日は来場者をチェックインして受付管理する。あわせてダッシュボードや各イベントの申込数・充足率を把握し、申込実績をCSV出力して運営に活かせる。

## 2. 前提・スコープ（確定）

| 項目 | 確定内容 |
|---|---|
| 認証 | 簡易ログイン（ダミー認証）。ログイン画面でメールアドレスを入力すると、そのユーザーのロールを自動判定して一般ユーザー／管理者それぞれの画面へ遷移する。あわせて、名前・メールアドレスのみで一般ユーザーを作成できる軽い会員登録（パスワードは扱わない）を用意する。パスワード認証・外部SSO・退会機能は実装対象外（技術仕様書§2）。管理者は登録経路を用意せず、固定の管理者アカウント（`admin@example.com`）のみとする。 |
| ロール | 「一般ユーザー」「管理者」の2種のみ。お気に入り登録・コメント投稿は両ロールとも可能。コメント削除は投稿者本人または管理者のみ。 |
| 承認フロー | なし。申込＝即「受付済」（区分の定員に空きがある場合）。管理者による承認・却下は行わない。 |
| イベントの公開 | 管理者が登録した時点で即公開（下書き状態は持たない）。 |
| 受付終了の扱い | 申込締切または開催日時を過ぎたイベントは、一覧に「受付終了」と表示し申込ボタンを非活性にする（一覧からは消さない）。 |
| 同時実行 | 定員ぎりぎりでの同時申込の競合制御は考慮しない（テスト段階の割り切り）。区分ごとの定員判定も同じ方針。 |
| 想定規模 | イベント数十件・申込数百件程度。PCブラウザ利用を前提。 |
| チーム独自機能 | 実装する（1件）。内容＝SC-05（申込状況・実績画面）でのイベント別 受付済申込数・充足率の表示、および申込数の多い順ソートによる人気度の把握。技術仕様書§3.1 の SC-05 必須要件は「集計結果のCSV等での出力」のみであり、画面上での集計表示・並び替えはそれを超える拡張と位置づける（DoD §8-7「チーム独自機能を最低1つ実装」を満たす）。 |
| 定員区分ごとの定員判定 | 区分（一般枠／会員枠等）があるイベントは区分単位で定員超過チェック・受付済数集計を行う。区分を持たないイベントはイベント単位（`events.capacity`）で判定する。 |

## 3. 利用者像（確定）

サークルやイベント運営者が企画するエンタメ系イベント（ボードゲーム会・スポーツ大会・ライブ・撮影会・
季節イベント等）の運営を想定する。ロールの呼び方は要件定義上「一般ユーザー」「管理者」のままとし、
実際の想定利用者（参加者／サークル運営者）はその役割の具体化として以下に記す。

### 一般ユーザー（参加者）

- 開催予定のイベントを一覧・検索・カレンダーで確認したい
- 気になるイベントに簡単に申し込みたい
- 参加区分（一般枠／会員枠など）を選んで申し込みたい
- 満席の人気イベントでも、キャンセル待ちとして申し込んでおきたい
- キャンセル待ちの場合、自分が何番目なのか知りたい
- 気になるイベントをお気に入り登録しておき、後からまとめて見たい
- 開催前でも開催後でも、そのイベントについて他の参加者とやり取りしたい
- 自分の申込状況（受付済／キャンセル待ち／キャンセル済）を確認したい
- 予定が変わったら申込を取り消したい
- （初めて使う場合）名前とメールアドレスだけで手軽に登録したい

### 管理者（サークル運営・イベント主催者）

- イベントを新規登録して公開したい
- どのサークル・誰が主催しているかを明記したい
- イベントに写真を付けて魅力的に見せたい
- 参加者に食事制限の有無などの追加質問をしたい
- 定員を複数の区分（一般枠／会員枠等）に分けて管理したい
- 登録済みイベントの内容の誤りを修正したい
- 中止・不要になったイベントを削除したい（誤って削除しても復元できるようにしたい）
- 当日、来場者をその場でチェックインして受付管理したい
- ダッシュボードで総イベント数・総ユーザー数・申込数をひと目で把握したい
- 各イベントの申込数・定員に対する充足率を把握し、人気企画を次回に活かしたい
- 申込実績（参加者名簿）をCSVで出力して当日の受付や報告に使いたい
- 登録済みユーザーの一覧を確認したい

## 4. 用語・状態の定義（確定）

| 用語 | 定義 |
|---|---|
| 申込ステータス | 「受付済」＝申込が有効な状態／「キャンセル待ち」＝定員超過時に登録された状態／「キャンセル済」＝利用者が取り消した状態。の3値（`applications.status`）。 |
| イベントの状態 | 画面上の状態は開催日時・申込締切から導出する（状態カラムは持たない）。申込締切前＝申込受付中、締切後または開催日時経過後＝受付終了。 |
| 充足率 | 受付済の申込数 ÷ 定員。 |
| 人気 | 受付済の申込数の多さで判断する。 |
| 承認 | 本システムでは行わない。 |
| 定員区分（チケット種別） | 1つのイベントに紐づく、独立した定員を持つ枠（例：「一般枠」定員30、「会員枠」定員10）。区分がある場合、申込は必ずいずれか1つの区分に対して行う。区分が無いイベントは、イベント全体を単一の枠として扱う。 |
| キャンセル待ちの順位 | 同一イベント（区分がある場合は同一区分）で、自分より`appliedAt`（申込日時）が古い「キャンセル待ち」の件数＋1。 |
| チェックイン | 管理者が、当日来場した申込者を「来場済み」として記録する操作。対象は「受付済」の申込のみ。 |
| お気に入り | 一般ユーザーが、後で見返したいイベントに付ける印。申込とは独立した情報（お気に入り＝申込ではない）。 |
| コメント | イベントに対して投稿できる自由記述のメッセージ。開催前後を問わず投稿可能。削除は投稿者本人または管理者のみ。 |

## 5. 業務シナリオ（正常系）

### 【一般】シナリオ1：イベントに申し込む

0. 一般ユーザーとしてログインする（メールアドレス入力、または初めての場合は名前・メールアドレスのみで会員登録する）
1. イベント一覧・検索・カレンダー表示から気になるイベント（例：「ボードゲーム交流会」）を選び、詳細で開催日時・主催者・定員・残り枠・申込締切を確認する
2. 区分（一般枠／会員枠等）があるイベントでは、申し込む区分を選ぶ。アンケート項目があれば回答する
3. 「申し込む」ボタンを押す
4. 申込完了画面で、ステータスが「受付済」（すでに満席の場合は「キャンセル待ち」）になったことを確認する

### 【一般】シナリオ2：申込状況の確認と取消

0. 一般ユーザーとしてログインする
1. 「マイページ（申込履歴）」を開き、自分が申し込んだイベントと各ステータス（受付済／キャンセル待ち／キャンセル済）、キャンセル待ちの場合は順位の一覧を見る
2. 参加をやめるイベントの「キャンセル」を押し、ステータスが「キャンセル済」に変わったことを確認する（受付済をキャンセルした場合、キャンセル待ちの人がいれば申込順に自動で繰り上がる）

### 【一般】シナリオ3：お気に入り・コメント・カレンダー活用

0. 一般ユーザーとしてログインする
1. イベント検索でキーワードを指定して絞り込み、気になるイベントを「お気に入り」に登録する
2. イベント詳細でコメント欄を開き、開催前に質問コメントを投稿する
3. イベント一覧をカレンダー表示に切り替え、お気に入り・申込済みのイベントが予定として見えることを確認する
4. マイページの「お気に入り」タブで、登録したイベントの一覧を確認する

### 【管理者】シナリオ1：イベントを登録・編集・削除する

0. 管理者としてログインする（ログイン直後はダッシュボードへ遷移する）
1. 管理画面で「イベント新規登録」を開き、イベント名・開催日時・定員・申込締切・場所・説明に加え、主催者名・画像URL・申込時アンケートの文言・区分（一般枠／会員枠等、複数）を入力して登録する（未入力の必須項目はその場でエラー表示される）
2. 一般ユーザー向けの一覧に、登録したイベントが主催者名・画像付きで表示されることを確認する
3. 登録済みイベントを開いて内容（定員など）を編集し、保存する
4. 不要になったイベントを削除し、一覧から消えることを確認する（受付済の申込が残っている場合は削除できない）。誤って削除した場合は、削除済みイベント画面から復元できる

### 【管理者】シナリオ2：申込状況の把握と実績出力

0. 管理者としてログインする
1. ダッシュボードで総イベント数・総ユーザー数・受付済の申込数（全イベント合計）を確認する
2. 管理画面のイベント一覧で、各イベントの受付済申込数・定員・充足率を確認する
3. 申込数の多い順に並び替え、人気のイベントを把握する
4. 「申込実績CSV出力」を押し、申込データ（イベント名・申込者名・申込日時・ステータス等）をCSVでダウンロードする

### 【管理者】シナリオ3：当日受付

0. 管理者としてログインする
1. 開催当日、対象イベントの「受付」画面を開き、申込者一覧（氏名・区分・ステータス・チェックイン状況）を表示する
2. 来場した申込者を選び「チェックイン」を押し、来場済みとして記録されることを確認する

## 6. 業務シナリオ（異常系）

| No | シナリオ | 期待する動作 |
|---|---|---|
| E1 | 定員（区分がある場合は区分）に達したイベントに申し込む | エラーにはせず、「キャンセル待ち」として登録する（201）。受付済の申込がキャンセルされると、申込順に自動で繰り上がる |
| E2 | 申込締切を過ぎた／開催日時を過ぎたイベントに申し込む | 申込は登録されず「申込受付は終了しました」を表示（400） |
| E3 | すでに「受付済」のイベントに同じユーザーが再度申し込む | 申込は追加されず「すでに申し込み済みです」を表示（400） |
| E4 | 「キャンセル済」または開催日時を過ぎた申込を取り消す | 取消不可「取消できません」を表示（400） |
| E5 | 申込がある（受付済1件以上）イベントを管理者が削除する | 削除不可「申込があるため削除できません」を表示（400） |
| E6 | 一般ユーザーが管理者用機能（イベント登録・編集・削除・CSV出力・受付等）を実行する | 権限エラー（HTTP 403）。画面上も管理メニューを表示しない |
| E7 | 管理者がイベントに申し込む | 申込不可「管理者は申込できません」を表示（403）。画面上も申込ボタンを表示しない |
| E8 | 「受付済」以外（キャンセル済・キャンセル待ち）の申込をチェックインしようとする | チェックイン不可「受付済の申込のみチェックインできます」を表示（400） |
| E9 | 同じイベントを二重にお気に入り登録する、または未登録のお気に入りを解除する | エラーにはせず、すでに希望通りの状態であれば成功として扱う（冪等） |
| E10 | 自分以外が投稿したコメントを削除しようとする（管理者以外） | 権限エラー「削除できません」を表示（403） |
| E11 | 存在しない、または対象イベントに属さない区分を指定して申し込む | 「指定された区分が見つかりません」を表示（404） |
| E12 | 区分があるイベントで区分を指定せず申し込む | 「区分を選択してください」を表示（400） |

## 8. 業務ルール／ロジック（確定）

| ロジック | 適用機能 | 許可条件（すべて満たすとき実行可） | 違反時の挙動 |
|---|---|---|---|
| 定員超過時の登録 | 8. 申込 | 受付済の申込数（区分がある場合は区分単位、無い場合はイベント単位）＜ 定員 → 「受付済」、達している → 「キャンセル待ち」で登録（エラーにしない） | - |
| 申込締切・日付チェック | 8. 申込 | 現在日時 ≦ 申込締切 かつ 現在日時 ＜ 開催日時 | 400「申込受付は終了しました」 |
| 二重申込チェック | 8. 申込 | 同一ユーザー×同一イベントに「受付済」または「キャンセル待ち」の申込が存在しない | 400「すでに申し込み済みです」 |
| 区分存在チェック | 8. 申込 | 指定した区分が対象イベントに属する | 404「指定された区分が見つかりません」（E11） |
| 区分必須チェック | 8. 申込 | 対象イベントに区分がある場合、区分の指定がある | 400「区分を選択してください」（E12） |
| 取消可否チェック | 10. キャンセル | 対象申込が「受付済」または「キャンセル待ち」 かつ 現在日時 ＜ 開催日時 | 400「取消できません」 |
| キャンセル待ちの繰り上げ | 10. キャンセル | 「受付済」の申込を取消した場合、同一イベント（区分がある場合は同一区分）で最も申込日時が古い「キャンセル待ち」を自動的に「受付済」へ変更する | - |
| キャンセル待ちの順位計算 | 9. 自分の申込一覧 | 対象申込より申込日時が古い、同一イベント（区分がある場合は同一区分）の「キャンセル待ち」件数＋1 | - |
| イベント削除可否チェック | 13. 削除 | 対象イベントに「受付済」の申込が存在しない | 400「申込があるため削除できません」 |
| ソフトデリート・復元 | 13. 削除／14. 復元 | 削除は物理削除ではなく削除日時を記録するのみ。復元は削除済みのものだけ対象 | 削除済みでないものの復元は404「削除済みイベントが見つかりません」 |
| 区分変更時の申込チェック | 12. イベント編集 | 区分（`ticketTypes`）を指定して保存する際、対象イベントに「受付済」または「キャンセル待ち」の申込が1件も無い（区分の無いイベントだった時点の申込も含む） | 400「区分に申込があるため変更できません」。キャンセル済の申込の履歴が区分を参照したまま残っている場合は400「区分に申込の履歴が残っているため変更できません」 |
| チェックイン可否チェック | 19. 当日受付 | 対象の申込ステータスが「受付済」 | 400「受付済の申込のみチェックインできます」（E8） |
| お気に入りの重複防止 | 17. お気に入り | 同一ユーザー×同一イベントの組み合わせは何度登録・解除してもエラーにしない（冪等） | - |
| コメント削除可否チェック | 18. コメント | 削除実行者が投稿者本人、または管理者 | 403「削除できません」（E10） |
| 権限チェック | 11〜16, 19 | ログイン中のロールが「管理者」 | 403（権限なし） |
| 権限チェック（一般限定） | 8. 申込 | ログイン中のロールが「一般」 | 403「管理者は申込できません」 |

> 技術仕様書§4.4の必須2類型：①上限・妥当性チェック＝定員超過チェック　②日付・状態チェック＝申込締切・日付チェック＋取消可否チェック＋イベント削除可否チェック＋チェックイン可否チェック。

## 9. 主要データ項目

| エンティティ | 主な項目 |
|---|---|
| `users`（利用者） | id ／ 氏名 ／ メールアドレス(UNIQUE) ／ ロール（general・admin） |

## 12. 申込実績CSV出力の仕様（機能15）

出力ロジックを定義する。列構成・文字コード等の技術的な詳細はAPI設計書_v2.0.md（API-09）を参照。

| 項目 | 仕様 |
|---|---|
| 出力対象イベント | 削除済み（ソフトデリート）でないイベントの申込のみを対象とする |
| 出力対象ステータス | 「受付済」「キャンセル待ち」「キャンセル済」のすべてを対象とする（ステータス列で区別できるため絞り込みは行わない） |
| 出力単位 | 1行＝1申込。区分（チケット種別）があるイベントは区分名も1列として出力する |
| 並び順 | `sort=startAt`（既定）：イベントの開催日時昇順→同一イベント内は申込日時昇順。`sort=accepted_desc`：イベントの受付済数の多い順→同一イベント内は申込日時昇順 |
| 出力形式 | UTF-8（BOM付き）のCSV。列構成・区切り文字・ファイル名等はAPI設計書_v2.0.md API-09に定める |
