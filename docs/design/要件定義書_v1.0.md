## 1. システム概要

- **システム名**：イベント申込システム
- **目的**：一般ユーザーはサークル・イベント運営者が企画したイベント（ボードゲーム会・スポーツ大会・ライブ・撮影会など）を一覧・検索・詳細で確認して申し込み、自分の申込状況（受付済／キャンセル待ち／キャンセル済）を確認・取消できる。管理者はイベントの登録・編集・削除を行い、ダッシュボードや各イベントの申込数・充足率を把握し、申込実績をCSV出力して運営に活かせる。

## 2. 前提・スコープ（確定）

| 項目 | 確定内容 |
|---|---|
| 認証 | 簡易ログイン（ダミー認証）。ログイン画面でメールアドレスを入力すると、そのユーザーのロールを自動判定して一般ユーザー／管理者それぞれの画面へ遷移する。あわせて、名前・メールアドレスのみで一般ユーザーを作成できる軽い会員登録（パスワードは扱わない）を用意する。パスワード認証・外部SSO・退会機能は実装対象外（技術仕様書§2）。管理者は登録経路を用意せず、固定の管理者アカウント（`admin@example.com`）のみとする。 |
| ロール | 「一般ユーザー」「管理者」の2種のみ。 |
| 承認フロー | なし。申込＝即「受付済」。管理者による承認・却下は行わない。 |
| イベントの公開 | 管理者が登録した時点で即公開（下書き状態は持たない）。 |
| 受付終了の扱い | 申込締切または開催日時を過ぎたイベントは、一覧に「受付終了」と表示し申込ボタンを非活性にする（一覧からは消さない）。 |
| 同時実行 | 定員ぎりぎりでの同時申込の競合制御は考慮しない（テスト段階の割り切り）。 |
| 想定規模 | イベント数十件・申込数百件程度。PCブラウザ利用を前提。 |
| チーム独自機能 | 実装する（1件）。内容＝SC-05（申込状況・実績画面）でのイベント別 受付済申込数・充足率の表示、および申込数の多い順ソートによる人気度の把握。技術仕様書§3.1 の SC-05 必須要件は「集計結果のCSV等での出力」のみであり、画面上での集計表示・並び替えはそれを超える拡張と位置づける（DoD §8-7「チーム独自機能を最低1つ実装」を満たす）。新規テーブルは追加しない（既存データの集計のみ）。 |
| 追加機能（任意、機能追加） | 上記の必須スコープに加え、利便性・体験向上のため以下を実装する：①会員登録・メールアドレスでのログイン、②イベント検索（キーワード・開催日範囲）、③管理者ダッシュボード（総イベント数・総ユーザー数・受付済申込数）、④管理者向けユーザー一覧、⑤定員超過時のキャンセル待ちと自動繰り上げ。いずれも新規テーブルは追加せず、既存の`users`／`events`／`applications`の範囲で実装する。 |

## 3. 利用者像（確定）

サークルやイベント運営者が企画するエンタメ系イベント（ボードゲーム会・スポーツ大会・ライブ・撮影会・
季節イベント等）の運営を想定する。ロールの呼び方は要件定義上「一般ユーザー」「管理者」のままとし、
実際の想定利用者（参加者／サークル運営者）はその役割の具体化として以下に記す。

### 一般ユーザー（参加者）

- 開催予定のイベントを一覧・検索で確認したい
- 気になるイベントに簡単に申し込みたい
- 満席の人気イベントでも、キャンセル待ちとして申し込んでおきたい
- 自分の申込状況（受付済／キャンセル待ち／キャンセル済）を確認したい
- 予定が変わったら申込を取り消したい
- （初めて使う場合）名前とメールアドレスだけで手軽に登録したい

### 管理者（サークル運営・イベント主催者）

- イベントを新規登録して公開したい
- 登録済みイベントの内容の誤りを修正したい
- 中止・不要になったイベントを削除したい
- ダッシュボードで総イベント数・総ユーザー数・申込数をひと目で把握したい
- 各イベントの申込数・定員に対する充足率を把握し、人気企画を次回に活かしたい
- 申込実績（参加者名簿）をCSVで出力して当日の受付や報告に使いたい
- 登録済みユーザーの一覧を確認したい

## 4. 用語・状態の定義（確定）

| 用語 | 定義 |
|---|---|
| 申込ステータス | 「受付済」＝申込が有効な状態／「キャンセル待ち」＝定員超過時に登録された状態（機能追加）／「キャンセル済」＝利用者が取り消した状態。の3値（`applications.status`）。 |
| イベントの状態 | 画面上の状態は開催日時・申込締切から導出する（状態カラムは持たない）。申込締切前＝申込受付中、締切後または開催日時経過後＝受付終了。 |
| 充足率 | 受付済の申込数 ÷ 定員。 |
| 人気 | 受付済の申込数の多さで判断する。 |
| 承認 | 本システムでは行わない。 |

## 5. 業務シナリオ（正常系）

### 【一般】シナリオ1：イベントに申し込む

0. 一般ユーザーとしてログインする（メールアドレス入力、または初めての場合は名前・メールアドレスのみで会員登録する）
1. イベント一覧、またはキーワード・開催日で絞り込めるイベント検索から気になるイベント（例：「ボードゲーム交流会」）を選び、詳細で開催日時・定員・残り枠・申込締切を確認する
2. 「申し込む」ボタンを押す
3. 申込完了画面で、ステータスが「受付済」（すでに満席の場合は「キャンセル待ち」）になったことを確認する

### 【一般】シナリオ2：申込状況の確認と取消

0. 一般ユーザーとしてログインする
1. 「マイページ（申込履歴）」を開き、自分が申し込んだイベントと各ステータス（受付済／キャンセル待ち／キャンセル済）の一覧を見る
2. 参加をやめるイベントの「キャンセル」を押し、ステータスが「キャンセル済」に変わったことを確認する（受付済をキャンセルした場合、キャンセル待ちの人がいれば申込順に自動で繰り上がる）

### 【管理者】シナリオ1：イベントを登録・編集・削除する

0. 管理者としてログインする（ログイン直後はダッシュボードへ遷移する）
1. 管理画面で「イベント新規登録」を開き、イベント名・開催日時・定員・申込締切・場所・説明を入力して登録する（未入力の項目はその場でエラー表示される）
2. 一般ユーザー向けの一覧に、登録したイベントが表示されることを確認する
3. 登録済みイベントを開いて内容（定員など）を編集し、保存する
4. 不要になったイベントを削除し、一覧から消えることを確認する（受付済の申込が残っている場合は削除できない）

### 【管理者】シナリオ2：申込状況の把握と実績出力

0. 管理者としてログインする
1. ダッシュボードで総イベント数・総ユーザー数・受付済の申込数（全イベント合計）を確認する
2. 管理画面のイベント一覧で、各イベントの受付済申込数・定員・充足率を確認する
3. 申込数の多い順に並び替え、人気のイベントを把握する
4. 「申込実績CSV出力」を押し、申込データ（イベント名・申込者名・申込日時・ステータス等）をCSVでダウンロードする

## 6. 業務シナリオ（異常系）

| No | シナリオ | 期待する動作 |
|---|---|---|
| E1 | 定員に達したイベントに申し込む（機能追加で仕様変更） | エラーにはせず、「キャンセル待ち」として登録する（201）。受付済の申込がキャンセルされると、申込順に自動で繰り上がる |
| E2 | 申込締切を過ぎた／開催日時を過ぎたイベントに申し込む | 申込は登録されず「申込受付は終了しました」を表示（400） |
| E3 | すでに「受付済」のイベントに同じユーザーが再度申し込む | 申込は追加されず「すでに申し込み済みです」を表示（400） |
| E4 | 「キャンセル済」または開催日時を過ぎた申込を取り消す | 取消不可「取消できません」を表示（400） |
| E5 | 申込がある（受付済1件以上）イベントを管理者が削除する | 削除不可「申込があるため削除できません」を表示（400） |
| E6 | 一般ユーザーが管理者用機能（イベント登録・編集・削除・CSV出力）を実行する | 権限エラー（HTTP 403）。画面上も管理メニューを表示しない |
| E7 | 管理者がイベントに申し込む | 申込不可「管理者は申込できません」を表示（403）。画面上も申込ボタンを表示しない |

## 8. 業務ルール／ロジック（確定）
