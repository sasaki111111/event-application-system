# イベント申込システム 要件定義（確定版）

フェーズA-1 成果物 ／ v1.1（2026-09-10。更新: チーム独自機能の位置づけ）

チーム開発演習（1人・教材作成テスト段階）／08_チーム開発演習_技術仕様書 v0.1 準拠。
「要件設計」シートのブレスト内容を、画面・API・DB設計に落とせる粒度へ整合・確定させたもの。

---

## 1. システム概要

- **システム名**：イベント申込システム
- **目的**：一般ユーザーは開催中のイベントを一覧・詳細で確認して申し込み、自分の申込状況（受付済／キャンセル済）を確認・取消できる。管理者はイベントの登録・編集・削除を行い、各イベントの申込数・充足率を把握し、申込実績をCSV出力して運営に活かせる。

---

## 2. 前提・スコープ（確定）

| 項目 | 確定内容 |
|---|---|
| 認証 | 簡易ログイン（ダミー認証）。固定ユーザーは一般1名・管理者1名を基本とし、ログイン画面でロールを選択して切り替える。パスワード認証・外部SSO・ユーザー登録機能は実装対象外（技術仕様書§2）。※時間に余裕があれば一般ユーザーをもう1名追加し、「本人分のみ」表示の分離を確認するテストを行う（任意）。 |
| ロール | 「一般ユーザー」「管理者」の2種のみ。 |
| 承認フロー | なし。申込＝即「受付済」。管理者による承認・却下は行わない。 |
| イベントの公開 | 管理者が登録した時点で即公開（下書き状態は持たない）。 |
| 受付終了の扱い | 申込締切または開催日時を過ぎたイベントは、一覧に「受付終了」と表示し申込ボタンを非活性にする（一覧からは消さない）。 |
| 同時実行 | 定員ぎりぎりでの同時申込の競合制御は考慮しない（テスト段階の割り切り）。 |
| 想定規模 | イベント数十件・申込数百件程度。PCブラウザ利用を前提。 |
| チーム独自機能 | 実装する（1件）。内容＝SC-05（申込状況・実績画面）でのイベント別 受付済申込数・充足率の表示、および申込数の多い順ソートによる人気度の把握。技術仕様書§3.1 の SC-05 必須要件は「集計結果のCSV等での出力」のみであり、画面上での集計表示・並び替えはそれを超える拡張と位置づける（DoD §8-7「チーム独自機能を最低1つ実装」を満たす）。新規テーブルは追加しない（既存データの集計のみ）。 |

## 3. 利用者像（確定）

### 一般ユーザー（申込者）

- 開催中のイベントを一覧・詳細で確認したい
- 興味のあるイベントに簡単に申し込みたい
- 自分の申込状況（受付されたか）を確認したい
- 予定が変わったら申込を取り消したい

### 管理者（主催・運営）

- イベントを新規登録して公開したい
- 登録済みイベントの内容の誤りを修正したい
- 中止・不要になったイベントを削除したい
- 各イベントの申込数・定員に対する充足率を把握したい
- 申込実績をCSVで出力して集計・報告に使いたい

---

## 4. 用語・状態の定義（確定）

| 用語 | 定義 |
|---|---|
| 申込ステータス | 「受付済」＝申込が有効な状態／「キャンセル済」＝利用者が取り消した状態。の2値のみ（`applications.status`）。 |
| イベントの状態 | 画面上の状態は開催日時・申込締切から導出する（状態カラムは持たない）。申込締切前＝申込受付中、締切後または開催日時経過後＝受付終了。 |
| 充足率 | 受付済の申込数 ÷ 定員。 |
| 人気 | 受付済の申込数の多さで判断する。 |
| 承認 | 本システムでは行わない。 |

## 5. 業務シナリオ（正常系）

### 【一般】シナリオ1：イベントに申し込む

0. 一般ユーザーとしてログインする
1. イベント一覧から興味のあるイベントを選び、詳細画面で開催日時・定員・残り枠・申込締切を確認する
2. 「申し込む」ボタンを押す
3. 申込完了画面で、ステータスが「受付済」になったことを確認する

### 【一般】シナリオ2：申込状況の確認と取消

0. 一般ユーザーとしてログインする
1. 「マイページ（申込履歴）」を開き、自分が申し込んだイベントと各ステータス（受付済／キャンセル済）の一覧を見る
2. 参加をやめるイベントの「取消」を押し、ステータスが「キャンセル済」に変わったことを確認する

### 【管理者】シナリオ1：イベントを登録・編集・削除する

0. 管理者としてログインする
1. 管理画面で「イベント新規登録」を開き、イベント名・開催日時・定員・申込締切・場所・説明を入力して登録する
2. 一般ユーザー向けの一覧に、登録したイベントが表示されることを確認する
3. 登録済みイベントを開いて内容（定員など）を編集し、保存する
4. 不要になったイベントを削除し、一覧から消えることを確認する

### 【管理者】シナリオ2：申込状況の把握と実績出力

0. 管理者としてログインする
1. 管理画面のイベント一覧で、各イベントの受付済申込数・定員・充足率を確認する
2. 申込数の多い順に並び替え、人気のイベントを把握する
3. 「申込実績CSV出力」を押し、申込データ（イベント名・申込者名・申込日時・ステータス等）をCSVでダウンロードする

## 6. 業務シナリオ（異常系）

| No | シナリオ | 期待する動作 |
|---|---|---|
| E1 | 定員に達したイベントに申し込む | 申込は登録されず「定員に達しています」を表示（API: HTTP 400） |
| E2 | 申込締切を過ぎた／開催日時を過ぎたイベントに申し込む | 申込は登録されず「申込受付は終了しました」を表示（400） |
| E3 | すでに「受付済」のイベントに同じユーザーが再度申し込む | 申込は追加されず「すでに申し込み済みです」を表示（400） |
| E4 | 「キャンセル済」または開催日時を過ぎた申込を取り消す | 取消不可「取消できません」を表示（400） |
| E5 | 申込がある（受付済1件以上）イベントを管理者が削除する | 削除不可「申込があるため削除できません」を表示（400） |
| E6 | 一般ユーザーが管理者用機能（イベント登録・編集・削除・CSV出力）を実行する | 権限エラー（HTTP 403）。画面上も管理メニューを表示しない |

## 7. 機能一覧（確定）

| No | 機能 | ロール | 対応シナリオ | 対応APIの型（技術仕様書§4.2） |
|---|---|---|---|---|
| 1 | ログイン | 全 | 各シナリオ 手順0 | （ダミー認証。API化は任意） |
| 2 | イベント一覧表示 | 一般 | 一般S1-1 | GET /api/events |
| 3 | イベント詳細表示 | 一般 | 一般S1-1 | GET /api/events/{id} |
| 4 | イベント申込 | 一般 | 一般S1-2 | POST /api/applications |
| 5 | 自分の申込一覧 | 一般 | 一般S2-1 | GET /api/my/applications |
| 6 | 申込キャンセル | 一般 | 一般S2-2 | DELETE /api/applications/{id} |
| 7 | イベント登録 | 管理者 | 管理S1-1 | POST /api/events |
| 8 | イベント編集 | 管理者 | 管理S1-3 | PUT /api/events/{id} |
| 9 | イベント削除 | 管理者 | 管理S1-4 | DELETE /api/events/{id}（必須8本＋の拡張） |
| 10 | 申込実績CSV出力 | 管理者 | 管理S2-3 | GET /api/reports/applications |

> 必須API 8本の型（技術仕様書§4.2）は No.2〜8＋10 で充足。No.9（イベント削除）は §4.2 の8本の型には無いが、SC-04（マスタ管理画面）の必須要件「登録・編集・削除（CRUD全操作）」に含まれるため必須。チーム独自機能は §2 参照。

## 8. 業務ルール／ロジック（確定）

| ロジック | 適用機能 | 許可条件（すべて満たすとき実行可） | 違反時の挙動 |
|---|---|---|---|
| 定員超過チェック | 4. 申込 | 受付済の申込数 ＜ 定員 | 400「定員に達しています」 |
| 申込締切・日付チェック | 4. 申込 | 現在日時 ≦ 申込締切 かつ 現在日時 ＜ 開催日時 | 400「申込受付は終了しました」 |
| 二重申込チェック | 4. 申込 | 同一ユーザー×同一イベントに「受付済」の申込が存在しない | 400「すでに申し込み済みです」 |
| 取消可否チェック | 6. キャンセル | 対象申込が「受付済」 かつ 現在日時 ＜ 開催日時 | 400「取消できません」 |
| イベント削除可否チェック | 9. 削除 | 対象イベントに「受付済」の申込が存在しない | 400「申込があるため削除できません」 |
| 権限チェック | 7〜10 | ログイン中のロールが「管理者」 | 403（権限なし） |

> 技術仕様書§4.4の必須2類型：①上限・妥当性チェック＝定員超過チェック　②日付・状態チェック＝申込締切・日付チェック＋取消可否チェック＋イベント削除可否チェック。

## 9. 主要データ項目（A-4 ER図・テーブル定義への引き継ぎ）

| エンティティ | 主な項目（型・制約の確定はA-4） |
|---|---|
| `users`（利用者） | id ／ 氏名 ／ メールアドレス(UNIQUE) ／ ロール（general・admin） |
| `events`（イベント） | id ／ イベント名 ／ 開催日時 ／ 場所 ／ 定員 ／ 申込締切日時 ／ 説明 ／ created_at ／ updated_at |
| `applications`（申込） | id ／ user_id(FK) ／ event_id(FK) ／ status（受付済・キャンセル済）／ 申込日時 ／ created_at ／ updated_at |

> 監査カラム created_at／updated_at は全テーブル必須（技術仕様書§4.3）。
