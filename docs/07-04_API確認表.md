## AP-01 ログイン `POST /api/login`

- **目的**：メールアドレスによる利用者識別（要件定義書F-01）。
- **呼び出し元**：SC-01 `login/login.ts` の `login()` → `LoginApiService.login()`。
- **Request**：`{ email: string }`
- **Validation**：`dto/LoginRequest.java` … `@NotBlank` `@Email`（Bean Validation、`@Valid @RequestBody`で自動実行）。
- **Controller**：`controller/UserController.java` `login()`（認証不要、`WebConfig`の`excludePathPatterns("/api/login", ...)`対象）。
- **Service**：`service/UserService.java` `login(email)` → `UserRepository.findByEmail(email)`。無ければ`UnauthorizedException`（401）。
- **Repository/DB**：`UserRepository.findByEmail` → `users`テーブルを`email`で検索（`uk_users_email`のユニークインデックス経由）。
- **Response（200）**：`UserResponse{ userId, name, email, role }`
- **エラー**：該当ユーザー無し→401「そのメールアドレスは登録されていません」。入力形式不正→400（`errors`配列）。
- **Frontend**：成功時`DummyUserStore.login(userId, role)`に保存し、`role`に応じ`/admin/dashboard`または`/events`へ`router.navigateByUrl`。401時は専用メッセージ、それ以外は`err.error?.message`を表示（`login.ts:56-61`）。
- **結果**：✓ 確認済み

## AP-12 イベント申込 `POST /api/applications`

- **目的**：参加申込の受付（F-05）。要件定義書§7の業務ルール（受付可否・区分要否・定員判定・二重申込防止）を実装する中核API。
- **呼び出し元**：SC-02展開部の`apply()`（`event-list.ts`）、SC-04 `event-detail.ts apply()` → `ApplicationApiService.apply(eventId, ticketTypeId?, extraAnswer?)`。
- **Request**：`ApplicationCreateRequest{ eventId(必須), ticketTypeId, extraAnswer(最大500) }`。
- **Validation**：`@NotNull eventId`はBean Validation。`ticketTypeId`の要否はService層（`resolveTicketType()`）で判定＝設計書どおり「区分が設定されたイベントでは必須」をコードで担保。
- **Controller**：`ApplicationController.apply()`。D-7方針：`requireGeneral()`（管理者は403）→手動`validate()`→`applicationService.apply()`。
- **Service**：`ApplicationService.apply()`：①`findByIdAndDeletedAtIsNull`で対象イベント確認（404）②`event.isOpen(now)`で受付期間チェック（400「申込受付は終了しました」）③`existsByUser_IdAndEvent_IdAndStatusIn`で二重申込チェック（受付済＋キャンセル待ちが対象、400「すでに申し込み済みです」）④`resolveTicketType()`で区分の要否・存在チェック（区分ありイベントで未指定→400、存在しないID→404）⑤悲観ロック取得（区分ありなら`findByIdAndEvent_IdForUpdate`、無ければ`findByIdForUpdate`）⑥受付済数と定員を比較し`ACCEPTED`または`WAITLISTED`を決定⑦`Application`を`save`。
- **Repository/DB**：`events`（存在確認・行ロック）、`ticket_types`（存在確認・行ロック）、`applications`（受付済数カウント・INSERT）。
- **Response（201）**：`ApplicationResponse{ id,eventId,ticketTypeId,userId,status,appliedAt }`
- **エラー**：管理者→403、受付終了／二重申込／区分未選択→400、イベント・区分不在→404。
- **Frontend**：成功時`router.navigate(['/events', eventId, 'done'], { state: { application } })`でSC-05へnavigation state付き遷移。
- **結果**：✓* 確認済み（`ApiIntegrationTest`複数＋`ApplicationServiceTest`多数＋同時実行の悲観ロックテスト`o01_同時に申し込んでも定員を超えて受付済にならない`）。本セッションで実MySQL上でも、区分単位の定員判定（定員1の区分に2人申込→1人受付済・1人キャンセル待ち）が正しく動作することを確認済み。
