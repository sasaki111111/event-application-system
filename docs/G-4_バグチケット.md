# G-4　バグチケット対応

## BUG-001：権限チェックより先にバリデーションが実行され、意図しないステータスコードが返る

| 項目 | 内容 |
|---|---|
| 起票日 | 2026-09-14 |
| 起票者 | Claude（D-7実装中の動作確認で発見） |
| 対象 | `EventController.create()` / `EventController.update()` / `ApplicationController.apply()` |
| 重要度 | 中（機能は壊れないが、意図しないエラー種別・情報が返る） |
| ステータス | 解決済み |

### 再現手順

1. 一般ユーザー（管理者ではない）としてログインした状態で `POST /api/events` に空のリクエストボディ（`{}`）を送る
2. レスポンスを確認する

### 期待する結果

要件定義書§8「権限チェック」により、リクエスト内容に関わらず **403 Forbidden**「権限がありません」が返るべき（バリデーションより権限チェックが優先されるべき）。

### 実際の結果（修正前）

**400 Bad Request**「入力エラー」（バリデーションエラーの詳細付き）が返っていた。原因は、`@Valid @RequestBody`によるBean Validationが、Controllerメソッドの本体（`requireAdmin()`呼び出し）が実行される**前**に、Spring MVCの引数解決の段階で走ってしまうため。同様の問題が`ApplicationController.apply()`（一般限定チェック）にもあった。

この結果、権限の無いユーザーが不正な入力を送った場合に、本来隠すべきバリデーションルールの詳細（`errors`配列）が先に見えてしまう、また期待するステータスコード（403）と異なる（400）という2つの問題があった。

### 原因

Spring MVCでは、`@Valid`付きの`@RequestBody`引数は、コントローラーメソッドの呼び出し前（引数解決の段階）でバリデーションされ、違反があれば`MethodArgumentNotValidException`がそこで投げられる。そのため、メソッド本体に書いた権限チェック（`requireAdmin()`等）より先にバリデーションが実行されてしまい、順序を制御できない。

### 修正内容

1. `EventController`・`ApplicationController`から`@Valid`アノテーションを削除
2. `jakarta.validation.Validator`をコンストラクタインジェクションで受け取る
3. 各メソッド内で「権限チェック（`requireAdmin()`/`requireGeneral()`）→手動バリデーション（`validator.validate(request)`）→本処理」の順に明示的に実行するよう変更
4. バリデーション違反時は`ConstraintViolationException`を投げるようにし、`GlobalExceptionHandler`に対応するハンドラーを追加（従来の`@Valid`失敗時と同じJSON形式のレスポンスを維持）

### 再テスト結果

| ケース | 修正前 | 修正後 |
|---|---|---|
| 一般ユーザーが不正な内容で`POST /api/events` | 400（バリデーション詳細） | **403**「権限がありません」 |
| 管理者が不正な内容で`POST /api/applications` | 400（バリデーション詳細） | **403**「管理者は申込できません」 |
| 管理者が空の内容で`POST /api/events`（権限チェック通過後） | 400 | 400「入力エラー」＋`errors`配列（変化なし、正しい） |
| 一般ユーザーが空の内容で`POST /api/applications`（権限チェック通過後） | 400 | 400「入力エラー」＋`errors`配列（変化なし、正しい） |

D-8（API手動疎通確認）・G-2（API/DB結合テスト）でも上記の権限チェック優先の挙動が壊れていないことを再確認済み。
