# 08_エラー設計書

## 1. 概要

本書は、本システムで発生しうるエラーを分類し、エラーID・発生条件・HTTPステータス・メッセージ・発生APIを一覧化するエラー設計書（エラーIDの台帳）である。`docs/06_詳細設計書.md`・`docs/07_バリデーション設計書.md`・`docs/09_認証認可設計書.md`で参照するエラーIDは、すべて本書8-3に登録する。

**本書の位置づけ（重要）**：8-1〜8-3・8-5〜8-7は、現在の実装（`GlobalExceptionHandler`・各種例外クラス・メッセージ文言）をそのまま体系化したものであり、実装と一致している。一方、8-2のエラーID体系（`E-V-`等の接頭辞）と、8-4で示す`code`フィールドは、現時点ではAPIレスポンスに含まれていない（現状のレスポンスは`docs/03_API設計書.md`2.3節のとおり`timestamp/status/error/message/errors`のみで、エラーIDに相当する項目を持たない）。本書のエラーIDは、他の設計書（バリデーション設計書・詳細設計書等）でエラーを一意に参照するための**文書上の識別子**として先行して整備するものであり、レスポンスへの`code`フィールド追加は、今後の実装対応として別途決定する。

## 8-1 エラー分類

`docs/01_要件定義書.md`「9. エラー要件」・`docs/03_API設計書.md`2.4節の7区分と、本書のエラーID接頭辞（8-2）の対応は次のとおり。

| 分類（01§9／03§2.4） | HTTPステータス | 例外の種類 | エラーID接頭辞 | このシステムでの実装 |
|---|---|---|---|---|
| 入力エラー | 400 | 業務例外 | `E-V-` | `MethodArgumentNotValidException`（`@Valid`使用時）、`ConstraintViolationException`（Controller内で手動検証する場合）、`HttpMessageNotReadableException`・`MethodArgumentTypeMismatchException`（リクエスト形式エラー） |
| 業務ルール違反エラー | 400 | 業務例外 | `E-B-` | `BusinessException` |
| データ未検出エラー | 404 | 業務例外 | `E-B-` | `NotFoundException`（業務ルール違反と同じ接頭辞とする。いずれも「利用者の操作で解決できる想定内の異常」であるため） |
| 認証エラー | 401 | 業務例外 | `E-A-` | `UnauthorizedException` |
| 権限エラー | 403 | 業務例外 | `E-A-` | `ForbiddenException` |
| リクエスト過多エラー | 429 | - | `E-R-` | `RateLimitInterceptor`（機能追加、`docs/10_非機能設計書.md`10-3）が、書き込み系API（POST/PUT/DELETE、ログインAP-01を含む）へのIPアドレス単位のアクセス回数を監視し、閾値超過時に返す。`GlobalExceptionHandler`は経由しない（Controllerに到達する前のHandlerInterceptorで判定するため） |
| 通信エラー | - | - | （エラーID無し） | サーバーに到達できない場合はHTTPステータス自体が得られないため、フロントエンドの`httpErrorInterceptor`がクライアント側で検知しメッセージを補う（`docs/06_詳細設計書.md`7-8参照）。サーバー側にエラーIDは存在しない |
| （該当区分無し。想定外の異常） | 500 | システム例外 | `E-S-` | `GlobalExceptionHandler`の`Exception`用ハンドラーが捕捉し、`E-S-001`として処理する。スタックトレースは画面に出さずログにのみ出力する（`docs/11_ログ設計書.md`11-6） |

|---|---|---|
| `E-V-` | 入力エラー（Validation。単項目チェック・相関チェック・リクエスト形式エラーを含む） | E-V-001〜 |

## 8-4 エラーレスポンスの形式

**現状の実装**（`docs/03_API設計書.md`2.3節、`ErrorResponse`クラス）：

```json
{
  "timestamp": "2026-09-24T17:04:23+09:00",
  "status": 401,
  "error": "Unauthorized",
  "message": "認証が必要です",
  "errors": null
}
```

入力値エラーの場合、`errors`にフィールドごとのエラーを配列で格納する。

```json
{
  "timestamp": "2026-09-24T17:04:23+09:00",
  "status": 400,
  "error": "Bad Request",
  "message": "入力エラー",
  "errors": [
    { "field": "name", "message": "名前を入力してください" }
  ]
}
```

| フィールド | 型 | 必須 | 内容 |
|---|---|:--:|---|
| timestamp | 日時（OffsetDateTime） | ○ | エラー発生日時 |
| status | 数値 | ○ | HTTPステータスコード |
| error | 文字列 | ○ | HTTPステータスの標準名（`Unauthorized`等） |
| message | 文字列 | ○ | 利用者向けメッセージ |
| errors | 配列 | - | 入力エラー（`MethodArgumentNotValidException`／`ConstraintViolationException`）のときのみ、項目ごとのエラー |

現状のレスポンスには8-2のエラーID（`code`に相当する項目）が含まれていない。8-1の位置づけのとおり、エラーIDをレスポンスに含める場合は`code`フィールドの追加が必要であり、これは今後の実装対応として別途決定する。

## 8-5 例外とステータスコードの変換

`GlobalExceptionHandler`（`@RestControllerAdvice`）が、全Controllerで発生した例外をまとめてHTTPステータスへ変換する。各Controllerに個別の例外処理は書かない。

| 例外クラス | 発生させる場所 | HTTP | 備考 |
|---|---|---|---|
| `UnauthorizedException` | `AuthInterceptor`（未ログイン）、`UserService#login`（該当利用者無し） | 401 | |
| `ForbiddenException` | `AuthContext#requireAdmin`、`ApplicationController#requireGeneral`、`ApplicationService#cancel`（本人以外）、`EventCommentService#delete`（権限なし） | 403 | |
| `NotFoundException` | 各Serviceの`orElseThrow`（イベント・申込・区分・コメント・利用者が対象） | 404 | |
| `BusinessException` | 各Serviceの業務ルール違反判定 | 400 | |
| `MethodArgumentNotValidException` | Spring（`@Valid`違反時に自動発生） | 400 | `errors`に項目ごとのエラーを詰める |
| `ConstraintViolationException` | Spring（Controller内で手動`validate()`を呼ぶ場合の`@Valid`相当） | 400 | 同上 |
| `HttpMessageNotReadableException` | Spring（不正なJSON等） | 400 | リクエスト形式エラー |
| `MethodArgumentTypeMismatchException` | Spring（パスパラメータの型不一致等） | 400 | リクエスト形式エラー |
| `Exception`（上記以外すべて） | `GlobalExceptionHandler#handleUnexpected` | 500 | E-S-001として処理する。スタックトレースはログにのみ出す（`docs/11_ログ設計書.md`11-6参照）。画面には内部情報を出さない（`application.yml`の`server.error.include-stacktrace: never`も参照） |

## 8-6 画面側の対応

`docs/04_画面設計書.md`の各画面が定める個別のエラー表示（例：SC-04「詳細の取得に失敗した場合は画面全体にエラーを表示する」）を前提に、HTTPステータス共通の振る舞いを整理する。

| HTTP | 画面の振る舞い | 実装場所 |
|---|---|---|
| 400 | レスポンスの`message`・`errors`を画面に表示する（`docs/07_バリデーション設計書.md`8-5） | 各画面コンポーネント |
| 401 | エラーメッセージをその場に表示する。ログイン画面（SC-01）のログイン失敗（E-A-006）も、サーバーが返すメッセージをそのまま表示する（画面側で「登録されていません」等の存在有無を断定する文言に言い換えない。`docs/09_認証認可設計書.md`9-8、`login.ts`） | 各画面コンポーネント |
| 403 | エラーメッセージをその場に表示する | 各画面コンポーネント |
| 404 | エラーメッセージを表示する | 各画面コンポーネント |
| 通信不可（status 0） | 「サーバーに接続できません。バックエンドが起動しているか確認してください。」と表示する（`docs/04_画面設計書.md`§2） | 共通（`httpErrorInterceptor`） |
| 500 | `GlobalExceptionHandler`が常に`message`「システムエラーが発生しました。時間をおいて再度お試しください」を返す。各画面は`err.error?.message`が無い場合（サーバーに到達する前の通信エラー等）に備え、既定メッセージも個別に用意している | 各画面コンポーネント |

**現状の制約（検討事項）**：401発生時に自動的にログイン画面へ遷移させる共通処理（`HttpInterceptor`等）は現時点では実装していない。`authGuard`が未ログイン状態での画面遷移そのものを防ぐため、通常操作で401が発生する場面は限定的（例：ログイン後にサーバー側のデータが直接操作された場合等）だが、発生した場合は各画面がその場にエラーメッセージを表示するのみで、自動ログアウト・自動遷移は行わない。将来的な改善事項として扱う。

## 8-7 メッセージ作成ルール

既存の実装で使われているメッセージ文言（8-3参照）から読み取れる方針は次のとおり。

- 「何が悪いか」を具体的に書く（例：「区分に申込があるため変更できません」）。可能な場合は「どうすればよいか」も含める（例：「定員を入力してください」）
- 内部情報（SQL文、スタックトレース、クラス名、テーブル名）は画面・メッセージに出さない
- 文末は「〜してください」（入力を促す）、「〜できません」（操作を拒否する）、「〜が見つかりません」（対象が存在しない）のいずれかに揃える
- 可変値を埋め込むメッセージ（例：残り枠数を含める等）は現状使用していない。将来追加する場合は埋め込み位置を明記する
