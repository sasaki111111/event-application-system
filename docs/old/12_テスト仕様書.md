# 12_テスト仕様書

## 1. 概要

本書は、イベント申込システムのテスト対象・テスト観点・テストケース・期待結果を定義するテスト仕様書である。`docs/01_要件定義書.md`〜`docs/11_ログ設計書.md`に定めた仕様を「どう確かめるか」に落とし込み、実装が設計どおりに動作することを確認する基準とする。

- 期待結果は、各設計書の記載（業務ルールID `R-xx`、エラーID `E-x-xxx`、画面ID `SC-xx`、API ID `AP-xx`）を根拠とし、本書独自の仕様は定めない。設計書と本書が食い違う場合は設計書を正とし、本書を見直す。
- `study-docs/14_チーム開発演習_技術仕様書_v0.1.md`6章「テスト・品質要件（最低ライン）」を満たすことを、本書の完了条件の一部とする（12-1参照）。

## 12-1 テスト方針

### テストレベル

| レベル | 目的 | 対象 | 実施方法 | 本書の章 | 技術仕様書6章の最低ライン |
|---|---|---|---|---|---|
| ユニットテスト（UT） | 業務ロジック（業務ルール・条件分岐）が単体で正しいことを確認する | Service層（`backend/src/main/java/.../service`） | JUnit5＋Mockito（Repositoryをモック化）。`mvnw test`で自動実行 | 12-3 | 業務ロジック1件につき正常系1・異常系1以上（最低4ケース） |
| API/DB結合テスト（IT） | Controller〜Service〜Repository〜DBを通して、APIの入出力・認証認可・エラー応答が正しいことを確認する | 全34 API（`docs/03_API設計書.md`） | `@SpringBootTest`＋`TestRestTemplate`（H2）で自動実行。自動化していないケースはSwagger UIまたはcurlで手動実施 | 12-4 | 必須API 8本のうち最低5本 |
| 画面テスト（UI） | 各画面の表示・入力・操作・遷移が画面設計書どおりであることを確認する | 全16画面（`docs/04_画面設計書.md`） | ブラウザでの手動確認 | 12-5 | - |
| 総合テスト（ST） | 利用者の業務の流れに沿って、画面→API→DBが連携して動作することを確認する | 一般利用者・管理者の業務シナリオ | ブラウザでの手動確認（シナリオ形式） | 12-6 | 一般利用者視点1本＋管理者視点1本（最低2本） |
| 非機能テスト（NF） | 排他制御・セキュリティ対策・障害時表示が設計どおりであることを確認する | `docs/10_非機能設計書.md`の各項目 | 自動テスト＋手動確認 | 12-7 | - |

### テスト観点

各テストケースは、次の観点のいずれかに分類する（表の「観点」列）。

| 観点 | 内容 |
|---|---|
| 正常 | 仕様どおりの入力・状態で、期待どおりの結果になること |
| 異常 | 業務ルール違反・データ未検出・権限なし等で、定められたエラーになること |
| 境界 | 上限・下限・期限ちょうど等、判定が切り替わる値での挙動 |
| 権限 | 認証・認可（ロール・本人判定）の挙動 |

### 合否判定

- 各ケースの「期待結果」をすべて満たした場合を合格（OK）、1つでも満たさない場合を不合格（NG）とする。
- エラー応答は、HTTPステータスと`message`（`docs/08_エラー設計書.md`8-3のメッセージ）の両方が一致することを確認する。入力エラー（E-V-xxx）は`errors[]`に該当フィールドが含まれることを確認する。
- 不合格のケースは12-9の手順でバグチケットを起票し、修正後に同じケースで再テストする。

### 自動化列の見方

12-3・12-4の「自動化」列は、対応する自動テストのメソッド名を示す（クラス名は各節の冒頭に記載。1ケースに複数のメソッドが対応する場合は「、」で区切る）。「未」は自動テストが無く、手動で実施するか今後自動化する候補であることを示す。

## 12-2 テスト環境・テストデータ

### テスト環境

| 区分 | UT・自動IT | 手動IT・UI・ST・NF |
|---|---|---|
| バックエンド | `mvnw test`（Spring Boot Test） | `mvnw spring-boot:run -Dspring-boot.run.profiles=local`（localhost:8080） |
| データベース | H2インメモリDB（MySQLモード。`src/test/resources/application.yml`）。テストごとに初期化 | MySQL 8.0（`eventapp`）。`schema.sql`→`seed.sql`を投入した状態から開始する |
| フロントエンド | - | `npm start`（localhost:4200） |
| ブラウザ | - | Google Chrome 最新版（開発者ツールのNetworkタブでAPIの応答を確認できること） |
| API確認ツール | - | Swagger UI（`http://localhost:8080/swagger-ui.html`）、curl |

### テストデータ

手動テストは、`seed.sql`投入直後の状態に次のデータを追加して実施する。TD-01〜TD-03は管理者で画面（SC-09）から登録し、TD-04は画面から作れないためSQLで用意する。

| ID | 内容 | 用意の方法 |
|---|---|---|
| TD-00 | `seed.sql`の利用者3件（ID=1 一般ユーザー `general@example.com`、ID=2 管理者 `admin@example.com`、ID=3 退会確認用ユーザー `withdraw-test@example.com`）とイベント51件 | `seed.sql` |
| TD-01 | 参加区分付きイベント「区分テスト」：区分「一般」定員1・「学生」定員1、アンケート文言「参加の目的を教えてください」、申込締切・開催日時は未来 | SC-09で登録 |
| TD-02 | 定員1のイベント「定員1テスト」（区分なし、アンケートなし） | SC-09で登録 |
| TD-03 | 申込締切が過去、開催日時が未来のイベント「締切済テスト」 | SC-09で登録（申込締切は過去日時を入力できる。`@Future`は開催日時のみ） |
| TD-04 | 開催日時が過去のイベント「開催済テスト」と、一般ユーザーの「受付済」申込1件 | TD-02と同様に登録・申込した後、`UPDATE events SET start_at = NOW() - INTERVAL 1 DAY, application_deadline = NOW() - INTERVAL 2 DAY WHERE name = '開催済テスト';` |
| TD-05 | 2人目の一般利用者「一般ユーザー2」`general2@example.com` | SC-01の新規登録 |

## 12-9 不具合の管理

1. テストでNGになったケースは、GitHubのIssueとして起票する（`.github/ISSUE_TEMPLATE/task.md`を使用）。タイトルは「[BUG] テストID 事象の要約」とし、本文に再現手順・期待結果（本書の記載）・実際の結果・発生環境を書く。
2. 修正は`feature/xxx`ブランチで行い、PRの本文に対応するIssueとテストIDを記載する。
3. マージ後、NGになったテストケースを再実施し、OKであればIssueをクローズする。関連するケース（同じ機能の他のテストID）も再実施する。
4. 修正内容が自動テストで確認できる場合は、同じ不具合の再発を防ぐため、対応する自動テストを追加する（本書の「自動化」列を「未」からメソッド名に更新する）。
