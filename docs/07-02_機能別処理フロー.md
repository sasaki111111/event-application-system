## フロー1：ログイン・新規登録（F-01・F-02）

```
① 利用者が /login を開く
  ↓ login/login.ts（Login）が表示される
② メールアドレスを入力し「ログイン」を押下
  ↓ login.ts login()（空欄なら通信せずエラー表示して終了）
③ LoginApiService.login(email) が POST /api/login を呼ぶ
  ↓ dummyAuthInterceptor（この時点ではDummyUserStoreが空のためヘッダ無し）
④ UserController.login()（AuthInterceptor対象外パス）
  ↓ @Valid LoginRequest（@NotBlank/@Email）
⑤ UserService.login(email)
  ↓ UserRepository.findByEmail(email)
⑥ 該当ユーザー無し → UnauthorizedException(401)
   該当あり → UserResponse{userId,name,email,role}を返す
⑦ GlobalExceptionHandler（401時）／Controllerがそのまま200で返却（成功時）
⑧ login.ts の subscribe.next / error
   成功: DummyUserStore.login(userId, role) に保存 → localStorage永続化
        role==='admin' なら router.navigateByUrl('/admin/dashboard')
        role==='general' なら '/events'
   失敗: err.status===401 なら固定メッセージ、それ以外はerr.error?.message
```

新規登録（F-02）はステップ③以降が `LoginApiService.register()` → `POST /api/users` → `UserController.register()` → `UserService.register()`（`existsByEmail`重複チェック→`role='general'`固定でINSERT）に差し替わり、成功時は`register()`のsubscribeがそのまま`DummyUserStore.login()`してログイン状態にしたうえで`/events`へ遷移する（設計書「登録と同時にログイン状態となる」と一致）。

以降の全リクエストでは`dummyAuthInterceptor`（`core/dummy-auth-interceptor.ts`）が`DummyUserStore.currentUserId()`を`X-User-Id`ヘッダとして自動付与し、backendの`AuthInterceptor`（`common/AuthInterceptor.java`）がそのヘッダから`UserRepository.findById()`でユーザーを解決し`AuthContext`に格納する、という往復がAPI設計書§0の認証方式そのものである。

## フロー2：イベント申込（キャンセル待ち込み）（F-05）

```
① 一般利用者がイベント一覧(SC-02)またはイベント詳細(SC-04)を開く
  ↓ EventList/EventDetail ngOnInit() → EventApiService.list()/detail() → GET /api/events(/id)
② 参加区分（設定時）・アンケート回答（設定時）を入力し「申し込む」を押下
  ↓ event-list.ts apply(eventId) または event-detail.ts apply()
③ ApplicationApiService.apply(eventId, ticketTypeId?, extraAnswer?)
  ↓ POST /api/applications { eventId, ticketTypeId, extraAnswer }
④ ApplicationController.apply()
   requireGeneral()（管理者なら403 ForbiddenException「管理者は申込できません」）
   ↓ validate(request)（手動Bean Validation、eventId必須のみ）
⑤ ApplicationService.apply(userId, eventId, ticketTypeId, extraAnswer)
   a. eventRepository.findByIdAndDeletedAtIsNull（無ければ404）
   b. event.isOpen(now) が false → BusinessException「申込受付は終了しました」(400)
   c. applicationRepository.existsByUser_IdAndEvent_IdAndStatusIn（受付済+キャンセル待ち）
      → 既にあれば BusinessException「すでに申し込み済みです」(400)
   d. resolveTicketType(): 区分ありイベントでticketTypeId未指定→400「区分を選択してください」
                            存在しないticketTypeId→404「指定された区分が見つかりません」
                            解決できた場合、区分の行を悲観ロック(SELECT...FOR UPDATE)
      区分無しイベントなら eventRepository.findByIdForUpdate() でイベント行を悲観ロック
   e. 受付済数(count) < 定員(capacity) ? ACCEPTED : WAITLISTED を判定
   f. Application を save（applied_atは現在時刻）
⑥ applicationRepository.save() → INSERT INTO applications(...)
⑦ ApplicationResponse{id,eventId,ticketTypeId,userId,status,appliedAt} を返す（201）
⑧ event-list.ts/event-detail.ts の subscribe.next
   router.navigate(['/events', eventId, 'done'], { state: { application } })
⑨ ApplyDone（SC-05）が navigation state から application を読み取り、
   status==='受付済' か 'キャンセル待ち' かで表示メッセージを出し分ける
```

**定員判定の排他制御**：ステップ⑤dのロック取得（悲観ロック、D-10で確定）により、同一イベント・同一区分への同時申込が直列化される。`ApiIntegrationTest.o01_同時に申し込んでも定員を超えて受付済にならない`で、定員1のイベントに2スレッドが同時にPOSTしても「受付済1件・キャンセル待ち1件」に必ず収まることを検証済み（実行結果：成功）。

## フロー3：申込キャンセルと自動繰り上げ（F-06）

```
① 利用者がマイページ(SC-06)を開く
  ↓ MyApplications ngOnInit → loadApplications() → GET /api/my/applications
② 対象の申込で「キャンセル」を押下 → confirm()で確認
  ↓ my-applications.ts cancel(application)
③ ApplicationApiService.cancel(id) → DELETE /api/applications/{id}
④ ApplicationController.cancel()（userIdはAuthContextから取得、リクエストに含めない）
⑤ ApplicationService.cancel(userId, applicationId)
   a. applicationRepository.findById（無ければ404）
   b. application.getUser().getId() != userId → ForbiddenException(403)
   c. cancellable = ACTIVE_STATUSES.contains(status) && now.isBefore(event.startAt)
      falseなら BusinessException「取消できません」(400)
   d. wasAccepted = status.equals(ACCEPTED) を記憶してから application.cancel()（→キャンセル済）
   e. wasAcceptedがtrueの場合のみ：
      対象行（区分があれば ticketTypeRepository.findByIdForUpdate、
              無ければ eventRepository.findByIdForUpdate）を悲観ロック
      → 同一区分/イベントで最古のキャンセル待ちを1件検索
        (findFirstByTicketType_IdAndStatusOrderByAppliedAtAsc または
         findFirstByEvent_IdAndTicketTypeIsNullAndStatusOrderByAppliedAtAsc)
      → 見つかれば application.promote()（→受付済に変更）
⑥ UPDATE applications SET status='キャンセル済' WHERE id=?
   （繰り上げ発生時）UPDATE applications SET status='受付済' WHERE id=?（別の1行）
⑦ 204 No Content を返す
⑧ my-applications.ts の subscribe.next → loadApplications() で一覧を再取得
  ↓ 自分の一覧には反映されるが、繰り上げられた「別の利用者」の申込状態は
    その利用者が次にマイページを開いた時にAPI-13で反映される（プッシュ通知等は無い）
```

キャンセル待ちの順位表示（`waitlistRank`）は`ApplicationService.calculateWaitlistRank()`が、自分より`appliedAt`が古い同一対象（区分単位/イベント単位）のキャンセル待ち件数+1を都度計算する方式（テーブル定義書§6「集計値を別途保持しない」方針と一致）。

## フロー4：イベント登録・編集（参加区分含む）（F-09）

```
① 管理者がイベント管理(SC-08)で「新規登録」または対象イベント名をクリック
  ↓ admin-event-list.html routerLink → /admin/events/new または /admin/events/:id/edit
② AdminEventForm ngOnInit()
   編集時: idParam有り → eventApi.detail(id) で初期値取得 → form.patchValue + ticketTypesArrayへpush
   新規時: 何もしない（空フォーム）
③ 管理者が項目を入力（参加区分は「区分を追加」でFormArrayに行を追加/削除）
④ 「保存」を押下 → admin-event-form.ts submit()
   クライアント側: form.invalid なら markAllAsTouched() して送信中止（Validators.required/min(1)）
   capacity = hasTicketTypes ? ticketTypesCapacitySum : 入力値（区分優先）
⑤ 新規: EventApiService.create(request) → POST /api/events
   編集: EventApiService.update(id, request) → PUT /api/events/{id}
⑥ EventController.create()/update()
   authContext.requireAdmin()（一般ユーザーなら403、D-7方針によりバリデーションより先に実行）
   ↓ validate(request)（手動、EventUpsertRequestの@NotBlank/@Size/@Future/@Min/@ValidEventDates）
⑦ EventService.create()/update()
   新規: new Event(...) → eventRepository.save()
   編集: findByIdOrThrow() → event.applyChanges(...)
   共通: saveTicketTypes(event, request.ticketTypes())
      requests==null → 既存区分を維持しつつcapacityを既存合計に同期（無ければ何もしない）
      requests!=null:
        existsByEvent_IdAndStatusIn(ACTIVE_STATUSES) が true → BusinessException(400)「区分に申込があるため変更できません」
        ticketTypeRepository.deleteByEvent_Id() で既存区分を全削除
          （DataIntegrityViolationException時 → 400「区分に申込の履歴が残っているため変更できません」）
        requests.isEmpty() → 区分0件で終了（capacityはrequest.capacity()のまま）
        区分名の重複チェック（distinctNames < requests.size() → 400「区分名が重複しています」）
        各区分をticketTypeRepository.save() → event.syncCapacityFromTicketTypes(合計)
⑧ DB: events テーブルへINSERT/UPDATE、ticket_types テーブルへDELETE→INSERT（全置換）
⑨ EventDetailResponse を返す（201/200）
⑩ admin-event-form.ts の subscribe.next → router.navigateByUrl('/admin/events')（SC-08へ）
   エラー時: 400+errors→フィールドごと表示／403→権限メッセージ／404→対象無しメッセージ
```

## フロー5：イベント削除・復元（F-10）

```
① 管理者がイベント管理(SC-08)で「削除」を押下 → confirm()
  ↓ admin-event-list.ts deleteEvent() → EventApiService.remove(id) → DELETE /api/events/{id}
② EventController.delete()（requireAdmin）
③ EventService.delete()
   countAccepted(id) = applicationRepository.countByEvent_IdAndStatus(id, "受付済")
   > 0 → BusinessException(400)「申込があるため削除できません」
   0   → event.softDelete()（deleted_atに現在時刻を設定。物理DELETEはしない）
④ UPDATE events SET deleted_at = NOW() WHERE id = ?
⑤ 204 No Content
⑥ 一般ユーザー向け一覧(AP-04)・詳細(AP-05)は findByIdAndDeletedAtIsNull / findAllByDeletedAtIsNull...
   を使うため、削除直後から一般ユーザーの目には見えなくなる

--- 復元 ---
⑦ 管理者が削除済みイベント(SC-10)で「復元」を押下 → confirm()
  ↓ admin-deleted-events.ts restoreEvent() → EventApiService.restore(id) → POST /api/events/{id}/restore
⑧ EventController.restore()（requireAdmin）→ EventService.restore()
   findByIdAndDeletedAtIsNotNull（削除済みでなければ404）→ event.restore()（deleted_at=null）
⑨ UPDATE events SET deleted_at = NULL WHERE id = ?
⑩ 復元後のEventDetailResponseを返す（200）→ 一般ユーザー一覧に即座に再表示される
```

## フロー6：当日受付・チェックイン（F-11）

```
① 管理者がイベント管理(SC-08)から対象イベントの「当日受付」を選択
  ↓ /admin/events/:id/checkin → AdminCheckin ngOnInit()
② CheckInApiService.attendees(eventId) → GET /api/events/{id}/attendees
③ EventController.attendees()（requireAdmin）→ ApplicationService.listAttendees()
   イベント存在確認 → applicationRepository.findByEvent_IdOrderByAppliedAtAsc()
   → AttendeeResponse[]（申込者名・区分名・状況・チェックイン日時、状況問わず全件）
④ 管理者が未チェックインの申込で「チェックイン」を押下
   attendee.checkedInAt が null → confirm無しで即実行
   attendee.checkedInAt が有り（再実行）→ confirm() で確認、キャンセルならAPI呼び出し中止
⑤ CheckInApiService.checkIn(applicationId) → PUT /api/applications/{id}/check-in
⑥ ApplicationController.checkIn()（requireAdmin）→ ApplicationService.checkIn()
   findById（無ければ404）→ status != ACCEPTED なら BusinessException(400)
   application.checkIn()（checked_in_atを現在時刻に設定／上書き）
⑦ UPDATE applications SET checked_in_at = NOW() WHERE id = ?
⑧ CheckInResponse{applicationId, checkedInAt} を返す（200）
⑨ admin-checkin.ts subscribe.next → loadAttendees() で一覧再取得、チェックイン日時が反映される
```

## フロー7：お気に入り登録・解除（F-07）

```
① 一覧(SC-02)・詳細(SC-04)でお気に入りボタンを押下
  ↓ event-list.ts/event-detail.ts toggleFavorite() → FavoriteStore.toggle(eventId)
② FavoriteStore.isFavorited(eventId) で現在状態を判定
   登録済み → FavoriteApiService.remove(eventId) → DELETE /api/favorites/{eventId}
   未登録   → FavoriteApiService.add(eventId)    → POST /api/favorites {eventId}
③ FavoriteController.add()/remove()
④ FavoriteService.add(): イベント存在確認(404) → 既存確認(findByUser_IdAndEvent_Id)
                          → 無ければ save()、有れば既存をそのまま返す（冪等）
   FavoriteService.remove(): deleteByUser_IdAndEvent_Id（0件でも例外なし、冪等）
⑤ DB: favorites テーブルへINSERT（新規時）またはDELETE
⑥ レスポンス: add=201(新規)/200(既存)、remove=204
⑦ FavoriteStore.toggle() が signal（ids）を楽観的に更新 → 画面のハートアイコン等が即座に反映
   （一覧・詳細・マイページが同じFavoriteStoreを共有するため、他画面でも状態が揃う）
```

マイページのお気に入りタブ（SC-06）だけは`FavoriteStore`を経由せず`FavoriteApiService.myFavorites()`を直接呼び、解除後は`favoriteStore.invalidate()`でキャッシュを破棄する設計（`favorite-store.ts`のコメント参照）。

## フロー8：イベントコメント投稿・削除（F-08）

```
① イベント詳細(SC-04)を開く → event-detail.ts loadComments()（ngOnInit内、詳細取得と並行）
  ↓ CommentApiService.list(eventId) → GET /api/events/{id}/comments
② EventCommentService.list() → requireEvent(404) → findByEvent_IdOrderByCreatedAtAscIdAsc()
   → 各コメントに mine=comment.isOwnedBy(currentUserId) を付与
③ コメント本文を入力し「投稿」を押下（本文が空ならevent-detail.ts postComment()が早期return）
  ↓ CommentApiService.post(eventId, body) → POST /api/events/{id}/comments {body}
④ EventCommentService.post() → requireEvent(404) → save(new EventComment(...))
⑤ INSERT INTO event_comments(...) → 201でEventCommentResponseを返す
⑥ event-detail.ts subscribe.next → commentBody.set('') + loadComments() で一覧再取得
⑦ 自分の投稿または管理者は「削除」ボタンが表示される（comment.mine判定、.html側）
   押下 → confirm() → CommentApiService.remove(commentId) → DELETE /api/comments/{id}
⑧ EventCommentService.delete(userId, isAdmin, commentId)
   findById(404) → !(isAdmin || comment.isOwnedBy(userId)) なら403「削除できません」
   → delete()
⑨ DELETE FROM event_comments WHERE id=? → 204 → loadComments()で一覧再取得
```

## フロー9：申込実績確認・CSV出力（F-12）

```
① 管理者が申込状況・実績(SC-12)を開く → admin-report.ts ngOnInit() → load()
  ↓ ReportApiService.summary('startAt') → GET /api/reports/applications?format=json&sort=startAt
② ReportController.report()（requireAdmin）→ ReportService.summarize(sort)
   findAllByDeletedAtIsNullOrderByStartAtAsc() → 各イベントごとに
   countByEvent_IdAndStatus(id,"受付済") と fillRate=round(accepted/capacity*100)/100 を算出
   sort=accepted_desc の場合のみ再ソート
③ EventReportResponse[] を返す（200）→ 集計テーブルを表示
④ 「並び順」を切替 → changeSort() → ②を再実行（sortパラメータのみ変更）
⑤ 「CSVダウンロード」を押下 → downloadCsv()
  ↓ ReportApiService.downloadCsv() → GET /api/reports/applications?format=csv（responseType:'blob'）
⑥ ReportController.report()（format==='csv'）→ ReportService.toCsv()
   findAllByEvent_DeletedAtIsNullOrderByEvent_StartAtAsc() を全件、
   BOM＋ヘッダ行＋各行「イベント名,申込者名,申込日時,ステータス」をCSVエスケープしつつ組み立て
⑦ Content-Type: text/csv;charset=UTF-8、Content-Disposition: attachment を付与して返す
⑧ admin-report.ts が Blob を受け取り、<a download> 要素を動的生成してクリック→保存
   （X-User-Idヘッダが必要なため直接URL遷移ではなくHttpClient経由、というコメント通りの実装）
```

```

  ↓ admin-user-list.ts registerAdmin() → UserApiService.registerAdmin(name,email)

⑦ admin-user-list.ts subscribe.next → フォームクリア + loadUsers() で一覧再取得
```
