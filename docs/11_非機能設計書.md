# 11_非機能設計書

## 1. 概要

本書は、本システムの非機能要件（性能・セキュリティ・可用性・保守性・運用等）についての目標・方針と、その実現方法を定義する非機能設計書である。`docs/01_要件定義書.md`「10. 非機能要件」の内容を、より具体的な設計判断として補足する位置づけとし、矛盾しないものとする。

## 11-1 前提

| 項目 | 想定 |
|---|---|
| 利用範囲 | 学内（自組織内）の利用者に限定する運用を前提とする（`docs/01_要件定義書.md`10.1節、D-02） |
| 利用者数・同時アクセス数・データ量 | 具体的な数値目標は定めない方針として確定している（`docs/06_設計確定時の確認事項.md`D-11）。小規模な組織内利用（大規模同時アクセスは非想定）を前提として設計判断を行う（D-10のロック方式選定の根拠と同じ前提） |
| 利用時間帯 | 定めない（D-11） |

## 11-2 性能

| 項目 | 目標・方針 | 実現方法 |
|---|---|---|
| 応答時間・同時アクセス数・稼働率 | 定量目標は定めない方針として確定している（`docs/01_要件定義書.md`10.3節、D-11） | - |
| 同時申込時の整合性 | 定員判定〜申込登録・繰り上げの間、対象行をロックして直列化する | 悲観ロック（`SELECT ... FOR UPDATE`）。`docs/07_詳細設計書.md`7-7、D-10参照 |
| 一覧の取得 | 現状はページングを行わず全件を返す（`docs/03_API設計書.md`AP-04等）。学内利用規模を前提に、件数増加時の対策は現時点で不要と判断している | - |
| 検索・集計の高速化 | よく検索・集計に使うカラムにインデックスを張る | `events.start_at`（`idx_events_start_at`）、`event_comments`の`(event_id, created_at)`（`idx_event_comments_event_created`）・`parent_comment_id`（`idx_event_comments_parent`）、`applications`の`(event_id, status, user_id)`（`idx_app_event_status_user`）・`(user_id, applied_at)`（`idx_app_user_applied`）・`(ticket_type_id, status)`（`idx_app_ticket_type_status`）（`backend/src/main/resources/db/schema.sql`） |
| CSV出力 | 目標時間は定めない（D-11） | 1申込あたり1行を都度整形して出力する単純な実装（`ReportService#toCsv`） |

## 11-3 セキュリティ

| 項目 | 目標・方針 | 実現方法 |
|---|---|---|
| SQLインジェクション | SQLに入力値を直接連結しない | Spring Data JPAのメソッドクエリ・`@Query`（名前付きパラメータ）を使用し、文字列連結によるSQL組み立ては行っていない |
| XSS（クロスサイトスクリプティング） | 入力値をそのままHTMLとして表示しない | Angularの補間（`{{ }}`）による自動エスケープを使用。`innerHTML`・`bypassSecurityTrust*`系APIは使用していない（未使用を確認済み） |
| 認可 | 権限のない操作をさせない | `docs/10_認証認可設計書.md`のとおり、サーバー側で全APIをチェックする（画面側のガードのみに依存しない） |
| 情報の漏えい | エラー画面・ログに内部情報や個人情報を出さない | `docs/09_エラー設計書.md`9-7（メッセージ作成ルール）、`docs/12_ログ設計書.md`12-6のとおり。ただし9-1で述べたとおり、500エラー（想定外の例外）は現時点で専用ハンドラーが無く、環境によってはSpring Bootの既定のエラー応答（開発時はスタックトレースを含みうる）がそのまま返る可能性があり、対応が必要な既知の課題である |
| 入力チェック | 不正な値を登録させない | `docs/08_バリデーション設計書.md`のとおり、サーバー側で必ずチェックする |
| 認証方式 | パスワードを用いない認証（D-02）で許容できる範囲を学内利用に限定する | `docs/10_認証認可設計書.md`10-1参照。学外公開等、利用範囲を拡大する場合は認証方式を改めて検討する |

## 11-4 可用性・データ整合性

| 項目 | 目標・方針 | 実現方法 |
|---|---|---|
| イベントの削除 | 申込等の履歴を保持したまま無効化する（物理削除しない） | `events.deleted_at`による論理削除（`docs/02_テーブル定義書.md`§6） |
| コメントの削除 | 返信が残っている場合は参照関係を保つため物理削除しない | `event_comments.deleted_at`による論理削除。返信が無い場合のみ物理削除する（D-18） |
| 定員・申込状況の算出 | 集計値を別途保持せず、申込データから都度算出する | `ApplicationRepository#countByEvent_IdAndStatus`等（`docs/02_テーブル定義書.md`§6） |
| バックアップ・障害復旧 | 方針は定めない（D-11） | 対象外 |
| 稼働率 | 目標は定めない（D-11） | 対象外 |
| 障害時の画面表示 | サーバーに接続できない場合、画面が真っ白にならないよう共通のメッセージを表示する | `httpErrorInterceptor`（`docs/04_画面設計書.md`§2） |

## 11-5 保守性・拡張性

| 項目 | 目標・方針 | 実現方法 |
|---|---|---|
| 層の分離 | 画面・API・DBの責務を混ぜない | Controller／Service／Repositoryの役割を一貫して守る（`docs/07_詳細設計書.md`7-2） |
| 重複の排除 | 同じ処理を複数箇所に書かない | 認可チェック（`AuthContext#requireAdmin`）、エラー整形（`GlobalExceptionHandler`）等を共通処理として集約する（`docs/07_詳細設計書.md`7-8） |
| 命名規約 | チーム内・実装全体で名前の付け方を揃える | クラス名はUpperCamelCase、DBのカラム名はsnake_case（`docs/02_テーブル定義書.md`） |
| API設計とSwagger UIの整合 | 実装から自動生成されるSwagger UIと`docs/03_API設計書.md`の内容を継続的に一致させる | D-15のとおり役割分担し、食い違いが生じた場合はSwagger UI（実装）を正として設計書側を見直す |
| 将来の拡張 | 参加区分・コメント返信等、当初のスキーマに無かった機能を追加できるようにする | `ticket_types`・`event_comments.parent_comment_id`のように、追加のテーブル・カラムで機能を積み増す設計とし、既存のカラムの意味を変更しない方針で運用してきた（`docs/06_設計確定時の確認事項.md`のD-07・D-18等） |

## 11-6 運用

| 項目 | 方針 |
|---|---|
| ログの確認 | エラー発生時の確認方法は`docs/12_ログ設計書.md`のとおり（ただし同書に記載のとおり、ログ出力自体は現時点で未実装） |
| 障害調査・監査のためのログ出力方針、スキーマ変更の管理方法（マイグレーション手順）、稼働環境（サーバー構成・コンテナ化・CI/CDの要否等） | いずれも定量的な方針は定めない方針として確定している（`docs/01_要件定義書.md`10.5節・10.6節、D-11） |
| 問い合わせ窓口 | 定めない（学内利用規模、D-11と同様の位置づけ） |

## 11-7 対象外事項

| 項目 | 理由 |
|---|---|
| 応答時間・同時アクセス数・稼働率等の定量目標 | 今後も定めない方針として確定している（D-11） |
| ログ出力方針・スキーマ変更管理方法・稼働環境 | 同上（D-11） |
| 本格的な認証（パスワード・SSO等） | 学内利用限定を前提に、現行のダミー認証方式を採用している（D-02）。範囲拡大時に改めて検討する |
| サーバーの冗長化・負荷分散、バックアップ | 学内利用規模を前提とし、対応方針を定めていない（D-11） |
| 一覧取得のページング | 現時点のデータ量では不要と判断している（11-2） |
