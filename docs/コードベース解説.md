# コードベース解説

このシステムの「frontend」「backend」「API」がそれぞれ何なのか、フォルダ・ファイル単位でどう役割分担しているのかをまとめたもの。公式の設計書（`docs/01_要件定義書.md`〜`docs/06_設計確定時の確認事項.md`。開発初期の旧版は`docs/design/`に残る）とは別に、コードを読むための補助資料として作成。

---

## 1. frontend・backend・APIの関係

### 1.1 全体像

```
【ブラウザ】
   ↓ 画面を表示
frontend（Angular、localhost:4200）
   ↓ データが欲しいときにAPIで問い合わせ
backend（Spring Boot、localhost:8080）
   ↓ データの読み書き
MySQL（eventappデータベース）
```

- frontendとbackendは**別々に起動する、別々のプログラム**（同じPC上で違う「部屋番号＝ポート」で動いている）
- frontendは画面（見た目）だけを担当し、データそのものは持っていない
- backendはデータ（DB経由）だけを担当し、画面は一切持っていない
- 両者をつなぐ「共通の言葉のルール」が **API**

### 1.2 例え

| 例え役 | 実際の役割 |
|---|---|
| 店員（frontend） | お客さん（人間）に見せる盛り付け・接客をする。食材は持っていない |
| 厨房（backend） | 食材（データ）を用意するだけ。盛り付けや接客はしない |
| 伝票（API） | 店員と厨房の間の「◯◯をください」「はいこれ」というやり取りの共通フォーマット |

### 1.3 APIとは何か（もう少し具体的に）

APIは、frontendとbackend**両方に実装されている、一致していなければならない約束事**。`docs/03_API設計書.md`（正式な基準。計25 API）で決めた内容が、実際には両側にこう対応している。

| 決めごと | frontend側の実装 | backend側の実装 |
|---|---|---|
| どのURLに聞くか | `core/event-api.ts` | `controller/EventController.java`の`@GetMapping` |
| 返ってくるデータの形 | `interface EventSummary {...}` | `dto/EventSummaryResponse.java` |
| 認証方法 | `login/login.ts`（メールアドレス入力）→`core/login-api.ts`（`/api/login`でロール判定、`/api/users`で新規登録）→`core/dummy-user-store.ts`（保持）→`core/dummy-auth-interceptor.ts`（`X-User-Id`ヘッダを付与） | `common/AuthInterceptor.java`（同ヘッダを検証）・`controller/UserController.java`（`/api/login`・`/api/users`） |
| エラーの形 | （受け取る側） | `common/exception/ErrorResponse.java` |

片方だけ変更するとズレて壊れるため、常にペアで考える必要がある。

## 2. フォルダ・ファイルの役割（詳細）

### 2.1 backend（`backend/src/main/java/com/example/eventapp/`）

Controller → Service → Repository という3層構造で、データがDBに近い方から遠い方へ流れる。

#### `entity/` — DBのテーブル1行をJavaのクラスとして表現

| ファイル | まとめられている内容 |
|---|---|
| `User.java` | `users`テーブル1行分（id・name・email・role等）。会員登録（機能追加）用のコンストラクタも持つ |
| `Event.java` | `events`テーブル1行分。「今受付中か」を判定する`isOpen()`、ソフトデリート用の`softDelete()`/`restore()`（機能追加）、定員区分の合計値に`capacity`を合わせる`syncCapacityFromTicketTypes()`（機能追加）、主催者名・画像URL・アンケート文言の列（機能追加）も持つ |
| `Application.java` | `applications`テーブル1行分。`User`・`Event`への参照に加え、申し込んだ定員区分への参照`TicketType`とアンケート回答`extraAnswer`（機能追加）、当日受付のチェックイン日時`checkedInAt`（機能追加。`checkIn()`で現在時刻に更新。再チェックインも同じメソッドで上書きする）も持つ |
| `ApplicationStatus.java` | `"受付済"`/`"キャンセル待ち"`/`"キャンセル済"`という文字列を定数化（あちこちに直書きしないため）。区分の全置換や取消可否の判定で使う「有効な状態」の集合`ACTIVE_STATUSES`（機能追加）も持つ |
| `TicketType.java` | `ticket_types`テーブル1行分（機能追加：定員区分）。1つの`Event`に複数ぶら下がり、区分ごとに独立した定員を持つ（例：「一般枠」定員30） |
| `Favorite.java` | `favorites`テーブル1行分（機能追加）。`User`・`Event`への参照のみを持つ単純な中間テーブル |
| `EventComment.java` | `event_comments`テーブル1行分（機能追加）。`Event`・`User`への参照と本文を持ち、削除可否チェックに使う`isOwnedBy(userId)`も持つ |

#### `repository/` — DBへの問い合わせ窓口

| ファイル | まとめられている内容 |
|---|---|
| `UserRepository.java` | `users`テーブルの検索（`AuthInterceptor`がログインユーザー確認に使う）。メール検索・重複チェック・一覧取得も持つ |
| `EventRepository.java` | `events`テーブルの検索（開催日時順の一覧取得など）。ソフトデリート（機能追加）により、通常の一覧・詳細用（`deletedAt IS NULL`）と削除済み一覧・復元用（`deletedAt IS NOT NULL`）のメソッドを分けて持つ。`findByIdForUpdate()`は同時申込時の排他制御（機能追加。`SELECT ... FOR UPDATE`で行ロックを取得するだけの用途で、業務上の存在チェックは兼ねない） |
| `ApplicationRepository.java` | `applications`テーブルの検索。受付済数のカウント・二重申込チェック用の存在確認に加え、区分単位の集計（機能追加：定員区分）、区分あり／無しそれぞれのキャンセル待ち繰り上げ対象取得・順位計算用のカウント（機能追加）も持つ。CSV出力用の一覧取得（`findAllByEvent_DeletedAtIsNullOrderByEvent_StartAtAsc()`）は削除済みイベントの申込を除外する（機能追加：申込実績のJSON集計と対象範囲を統一） |
| `TicketTypeRepository.java` | `ticket_types`テーブルの検索（機能追加）。イベントに紐づく区分一覧の取得、申込時の区分存在チェック、区分の全置換時の一括削除を持つ。`findByIdAndEvent_IdForUpdate()`／`findByIdForUpdate()`は同時申込時の排他制御用（機能追加。前者は区分の存在検証とロック取得を兼ねる） |
| `FavoriteRepository.java` | `favorites`テーブルの検索（機能追加）。ユーザー×イベントでの1件取得（冪等な登録に使う）・解除・自分の一覧取得を持つ |
| `EventCommentRepository.java` | `event_comments`テーブルの検索（機能追加）。イベントごとのコメント一覧を投稿日時順（同一秒内はid順）で取得する |
| `package-info.java` | このフォルダ自体の役割説明（実行されるコードではない） |

中身はほぼ空だが、Spring Data JPAがメソッド名から自動でSQLを生成して実装してくれる。

#### `service/` — 業務ロジック（計算・判断）

| ファイル | まとめられている内容 |
|---|---|
| `EventService.java` | イベントの一覧・詳細・登録・編集・削除。`acceptedCount`・`open`・`remaining`の計算、削除時の「申込があれば拒否」判定。削除は物理削除ではなくソフトデリート（`deletedAt`を立てるのみ）で、削除済み一覧の取得・復元も持つ（機能追加）。定員区分（機能追加）を指定して登録・編集すると、既存の区分を全置換（削除→再作成）し`capacity`を区分の合計に同期する。対象の区分に有効な申込が残っている場合は変更を拒否し、同一イベント内で区分名が重複している場合も拒否する（機能追加） |
| `ApplicationService.java` | イベント申込。締切超過・二重申込のチェックを行い、定員（区分がある場合は区分単位、無ければイベント単位）に空きがあれば「受付済」・無ければ「キャンセル待ち」で登録する（機能追加）。区分があるイベントでは区分の指定必須・存在チェックも行う。受付済のキャンセル時は、同一区分（区分が無ければ同一イベント）で最も古いキャンセル待ちを自動で繰り上げ、自分の申込一覧ではキャンセル待ちの順位も計算する（機能追加）。定員判定から申込登録・繰り上げまでの間は、対象行（区分があれば区分、無ければイベント）を悲観ロック（`SELECT ... FOR UPDATE`）で直列化し、同時申込による定員超過を防ぐ（機能追加）。当日受付の申込者一覧取得・チェックイン（「受付済」のみ対象、再チェックインは日時を上書き）も持つ（機能追加） |
| `FavoriteService.java` | お気に入りの登録・解除・一覧（機能追加）。登録・解除はどちらも冪等（同じ状態への操作を繰り返してもエラーにしない）。登録が新規作成か既存の再利用かを`FavoriteAddResult`（同ファイル内の小さな内部型）でControllerに伝え、HTTPステータス（201/200）の出し分けに使う |
| `EventCommentService.java` | イベントコメントの一覧・投稿・削除（機能追加）。削除は投稿者本人または管理者のみ許可する |
| `ReportService.java` | 申込実績の集計（JSON、チーム独自機能）とCSV出力。JSON集計はイベント別の受付済数・充足率を計算し`sort`指定で並び替え可能。CSVは開催日時順の申込明細をUTF-8 BOM付きで返す。どちらも削除済みイベントの申込は対象外とし、対象範囲を統一している |
| `UserService.java` | メールアドレスでのログイン・軽い会員登録・ユーザー一覧・管理者アカウント登録（いずれも機能追加）。パスワードは扱わない。`register()`は常に一般ユーザー、`registerAdmin()`は常に管理者を作成する |
| `PingService.java` | 起動確認用の最小サンプル（`"pong"`を返すだけ） |

> G-2の結合テストを作る過程で、`Event`・`Application`の`created_at`/`updated_at`列がテスト用H2スキーマ（Hibernateがエンティティ定義から自動生成）だとNOT NULLなのにDEFAULT値が無く、INSERTが失敗する問題が見つかった。本番用の`db/schema.sql`には`DEFAULT CURRENT_TIMESTAMP`があるが、Hibernateの自動生成スキーマはそれを知らないため。エンティティの`@Column`に`columnDefinition`を追加して解決した（本番は`ddl-auto: none`のため影響なし）。

### 2.2 frontend（`frontend/src/app/`）

Angularでは、1つの画面・機能につき`.ts`（データと動き）・`.html`（画面の構造）・`.css`（見た目）の3点セットで作る。

定員区分・お気に入り・イベントコメント・当日受付・イベント検索・カレンダー表示・管理者アカウント登録は、backend・frontendとも実装済み。

#### `core/` — API通信など、画面をまたいで共通で使うもの

| ファイル | まとめられている内容 |
|---|---|
| `event-api.ts` | backendの`/api/events`系API（一覧・詳細・登録・編集・削除）を呼び出す窓口。データの型もここで定義。削除済み一覧・復元（機能追加）も持つ |
| `application-api.ts` | backendの`/api/applications`（イベント申込・マイページ・キャンセル）を呼び出す窓口 |
| `favorite-api.ts` | backendの`/api/favorites`・`/api/my/favorites`（お気に入りの登録・解除・一覧）を呼び出す窓口（機能追加） |
| `favorite-store.ts` | お気に入り登録状況（イベントIDの集合）を画面間で共有するストア（機能追加）。`event-list`・`event-detail`・`my-applications`が個別にAPIを呼ぶ重複を解消するために導入 |
| `comment-api.ts` | backendの`/api/events/{id}/comments`・`/api/comments/{id}`（イベントコメントの一覧・投稿・削除）を呼び出す窓口（機能追加） |
| `checkin-api.ts` | backendの`/api/events/{id}/attendees`・`/api/applications/{id}/check-in`（当日受付の申込者一覧・チェックイン）を呼び出す窓口（機能追加） |
| `report-api.ts` | backendの`/api/reports/applications`（申込実績のJSON集計・CSVダウンロード）を呼び出す窓口 |
| `user-api.ts` | backendの`/api/users`（GET、管理者専用のユーザー一覧）・`/api/admins`（POST、管理者アカウント登録）を呼び出す窓口（機能追加） |
| `dummy-auth-interceptor.ts` | 送信する全リクエストに`X-User-Id`ヘッダを自動で付ける仕組み。どのuserIdを付けるかはログイン画面（`login/`）で入力・確認されたIDをDummyUserStoreから読む |
| `login-api.ts` | ログイン画面から呼ぶ認証不要のAPI窓口。`/api/login`（メールアドレスでログイン）・`/api/users`（POST、会員登録）を呼び出す |
| `http-error-interceptor.ts` | 全リクエストのエラーを共通処理する仕組み（E-1）。バックエンドに繋がらない場合（status 0）のメッセージを一箇所にまとめ、各画面は`err.error?.message`を読むだけでよくする |
| `dummy-user-store.ts` | ログイン中のユーザー（ダミー認証の`userId`・`role`）を覚えておく入れ物（E-2）。未ログイン時はどちらも`null`。`isAdmin()`は`role`が`admin`かどうかを返す（管理者判定はバックエンドが返す`role`に基づき統一。以前は`userId === '2'`という決め打ちだった） |
| `auth-guard.ts` | 未ログイン（`userId`が`null`）で保護ルートに来た場合に`/login`へ戻すルートガード（E-2） |
| `admin-guard.ts` | `/admin/**`への画面遷移を、`dummy-user-store.ts`の`isAdmin()`が`false`の場合は`/events`に戻すルートガード（`auth-guard.ts`の後段） |

#### `login/` — SC-01 ログイン画面

| ファイル | まとめられている内容 |
|---|---|
| `login.ts`/`.html`/`.css` | ログイン画面（`/login`）。パスワードは無く、メールアドレスを入力すると`login-api.ts`経由でロールを判定し、一般ユーザー／管理者それぞれの初期画面へ自動的に遷移する（ダミー認証）。名前・メールアドレスだけで一般ユーザーを作れる会員登録欄も持つ |

#### `events/` — イベントに関する画面（一般ユーザー向け）

| フォルダ | まとめられている内容 |
|---|---|
| `event-list/` | イベント一覧画面（`/events`）。`.ts`=一覧取得のロジック、`.html`=表の構造、`.css`=バッジ等の装飾。行を展開（▼）すると詳細取得＋その場で申込もできる。一覧形式とカレンダー形式（機能追加。月単位、前月・翌月切替）の表示切替、お気に入りの登録・解除ボタン（機能追加）も持つ。管理者には申込フォームを表示しない（`isAdmin()`で判定） |
| `event-search/` | イベント検索画面（`/events/search`、機能追加）。一覧を全件取得し、キーワード（イベント名・場所）・開催日範囲でフロント側のみ絞り込む |
| `event-detail/` | イベント詳細＋申込画面（`/events/:id`）。詳細表示に加えて「申し込む」ボタン（区分・アンケート回答の入力を含む）、お気に入りの登録・解除（機能追加）、コメントの一覧・投稿・削除（機能追加。自分の投稿または管理者のみ削除ボタンを表示）を持つ。`?from=search`付きで来た場合は「戻る」の行き先が検索画面になる |
| `apply-done/` | 申込完了画面（`/events/:id/done`）。申込APIのレスポンスをそのまま表示するだけの画面。ルーターのnavigation stateで結果を受け取るため、直接アクセス・再読み込みでは結果を表示できない |

#### `admin/` — 管理者向け画面

| フォルダ | まとめられている内容 |
|---|---|
| `admin-dashboard/` | ダッシュボード画面（`/admin/dashboard`、機能追加。管理者ログイン直後の遷移先）。総イベント数・総ユーザー数・受付済の申込数（全イベント合計）を、既存のイベント一覧・ユーザー一覧・申込実績APIを組み合わせて表示する |
| `admin-event-list/` | イベント管理一覧画面（`/admin/events`）。一覧表示に加えて編集リンク・削除ボタンを持つ。削除済みイベント画面・当日受付画面へのリンクも持つ |
| `admin-deleted-events/` | 削除済みイベント確認・復元画面（`/admin/events/deleted`、機能追加）。ソフトデリートされたイベントを一覧表示し、「復元」ボタンで元に戻せる |
| `admin-event-form/` | イベント登録・編集フォーム（`/admin/events/new`・`/admin/events/:id/edit`）。ルートに`:id`があれば編集、無ければ新規登録として動く1つのコンポーネント。参加区分（区分名・定員の行を追加/削除、機能追加）を1件以上入力すると定員欄は区分の合計を自動表示する |
| `admin-checkin/` | 当日受付画面（`/admin/events/:id/checkin`、機能追加）。指定イベントの申込者一覧を表示し、「受付済」の申込にチェックインボタンを表示する。チェックイン済みの申込には「再チェックイン」ボタンを常に表示し、押下すると確認ダイアログを出したうえでチェックイン日時を上書きする |
| `admin-report/` | 申込状況・実績画面（`/admin/reports`）。イベント別の受付数・充足率のJSON集計表示とCSVダウンロードボタンを持つ |
| `admin-user-list/` | 利用者管理画面（`/admin/users`）。登録済み利用者（ID・名前・メール・ロール）の一覧と、名前・メールアドレスを入力して新たな管理者アカウントを登録するフォーム（機能追加）を持つ |

#### `my-applications/` — 一般ユーザーのマイページ

| ファイル | まとめられている内容 |
|---|---|
| `my-applications.ts`/`.html`/`.css` | マイページ（`/my/applications`）。タブ切替で「申込一覧」（受付済・キャンセル待ち（機能追加）・キャンセル済のバッジ表示、「キャンセル」ボタンは受付済・キャンセル待ちの両方で表示）と「お気に入り」（機能追加。登録済みイベントの一覧と解除ボタン）を切り替えて表示する |

#### `not-found/` — 404画面

| ファイル | まとめられている内容 |
|---|---|
| `not-found.ts`/`.html`/`.css` | 定義されていないURLへのアクセス時に表示する画面（機能追加）。ログイン状態によらず表示でき、「イベント一覧に戻る」ボタンを持つ |

#### ルート直下（`src/app/`）— アプリ全体の骨組み

| ファイル | まとめられている内容 |
|---|---|
| `main.ts` | ブラウザが最初に実行するファイル。アプリを起動する |
| `app.ts` / `app.html` / `app.css` | 一番外側の部品。共通ナビ（`dummy-user-store.ts`の`isAdmin()`で管理者向け「ダッシュボード／イベント管理／申込状況・実績／利用者管理」と一般向け「イベント一覧／イベント検索／マイページ」を出し分け、共通で「ログアウト」）＋`router-outlet`（画面の差し込み口） |
| `app.config.ts` | HttpClient・Routerなど、アプリ全体に効く設定をまとめる場所。HttpClientには`dummyAuthInterceptor`（認証ヘッダ付与）と`httpErrorInterceptor`（通信エラーの共通化）を登録 |
| `app.routes.ts` | URL（`/login`・`/events`・`/admin/events`等）とコンポーネントの対応表。保護ルートには`auth-guard.ts`、管理者用ルートにはさらに`admin-guard.ts`を適用。定義されていないURLは末尾のワイルドカードルートで`not-found/`に流す |
| `app.spec.ts` | `app.ts`のテストコード |

#### `src/`直下（`app/`の外）

| ファイル | まとめられている内容 |
|---|---|
| `index.html` | ブラウザが最初に読み込むHTML（中身は`<app-root>`だけ） |
| `styles.css` | アプリ全体に効くグローバルスタイル（現時点では未使用） |
