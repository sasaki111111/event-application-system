# コードベース解説

このシステムの「frontend」「backend」「API」がそれぞれ何なのか、フォルダ・ファイル単位でどう役割分担しているのかをまとめたもの。公式の設計書（`docs/design/`）とは別に、コードを読むための補助資料として作成。

---

## 1. frontend・backend・APIの関係

### 1.1 全体像

```
【ブラウザ】
   ↓ 画面を表示
frontend（Angular、localhost:4200）
   ↓ データが欲しいときにAPIで問い合わせ
backend（Spring Boot、localhost:8080）
   ↓ データの読み書き
MySQL（eventappデータベース）
```

- frontendとbackendは**別々に起動する、別々のプログラム**（同じPC上で違う「部屋番号＝ポート」で動いている）
- frontendは画面（見た目）だけを担当し、データそのものは持っていない
- backendはデータ（DB経由）だけを担当し、画面は一切持っていない
- 両者をつなぐ「共通の言葉のルール」が **API**

### 1.2 例え

| 例え役 | 実際の役割 |
|---|---|
| 店員（frontend） | お客さん（人間）に見せる盛り付け・接客をする。食材は持っていない |
| 厨房（backend） | 食材（データ）を用意するだけ。盛り付けや接客はしない |
| 伝票（API） | 店員と厨房の間の「◯◯をください」「はいこれ」というやり取りの共通フォーマット |

### 1.3 APIとは何か（もう少し具体的に）

APIは、frontendとbackend**両方に実装されている、一致していなければならない約束事**。`docs/design/API設計書_v1.1.md`で決めた内容が、実際には両側にこう対応している。

| 決めごと | frontend側の実装 | backend側の実装 |
|---|---|---|
| どのURLに聞くか | `core/event-api.ts` | `controller/EventController.java`の`@GetMapping` |
| 返ってくるデータの形 | `interface EventSummary {...}` | `dto/EventSummaryResponse.java` |
| 認証方法 | `core/dummy-auth-interceptor.ts`（`X-User-Id`ヘッダを付与） | `common/AuthInterceptor.java`（同ヘッダを検証） |
| エラーの形 | （受け取る側） | `common/exception/ErrorResponse.java` |

片方だけ変更するとズレて壊れるため、常にペアで考える必要がある。

## 2. フォルダ・ファイルの役割（詳細）

### 2.1 backend（`backend/src/main/java/com/example/eventapp/`）

Controller → Service → Repository という3層構造で、データがDBに近い方から遠い方へ流れる。

#### `entity/` — DBのテーブル1行をJavaのクラスとして表現

| ファイル | まとめられている内容 |
|---|---|
| `User.java` | `users`テーブル1行分（id・name・email・role等） |
| `Event.java` | `events`テーブル1行分。「今受付中か」を判定する`isOpen()`も持つ |
| `Application.java` | `applications`テーブル1行分。`User`・`Event`への参照を持つ |
| `ApplicationStatus.java` | `"受付済"`/`"キャンセル済"`という文字列を定数化（あちこちに直書きしないため） |

#### `repository/` — DBへの問い合わせ窓口

| ファイル | まとめられている内容 |
|---|---|
| `UserRepository.java` | `users`テーブルの検索（`AuthInterceptor`がログインユーザー確認に使う） |
| `EventRepository.java` | `events`テーブルの検索（開催日時順の一覧取得など） |
| `ApplicationRepository.java` | `applications`テーブルの検索（受付済数のカウントなど） |
| `package-info.java` | このフォルダ自体の役割説明（実行されるコードではない） |

中身はほぼ空だが、Spring Data JPAがメソッド名から自動でSQLを生成して実装してくれる。

#### `service/` — 業務ロジック（計算・判断）

| ファイル | まとめられている内容 |
|---|---|
| `EventService.java` | イベント一覧・詳細取得。`acceptedCount`（受付済数）・`open`（受付中か）・`remaining`（残り枠）の計算 |
| `PingService.java` | 起動確認用の最小サンプル（`"pong"`を返すだけ） |

#### `dto/` — APIでやり取りするJSONの形の定義

| ファイル | まとめられている内容 |
|---|---|
| `EventSummaryResponse.java` | イベント一覧APIが返す1件分の形 |
| `EventDetailResponse.java` | イベント詳細APIが返す形（一覧の項目＋説明文・残り枠） |

DBの`Event`エンティティをそのまま返さず、必要な項目だけに変換して渡すためのもの。

#### `controller/` — HTTPリクエストの入口

| ファイル | まとめられている内容 |
|---|---|
| `EventController.java` | `GET /api/events`（一覧）・`GET /api/events/{id}`（詳細） |
| `PingController.java` | `GET /api/ping`（起動確認）・`GET /api/whoami`（認証確認、開発用） |

#### `common/` — 全APIに共通の仕組み

| ファイル | まとめられている内容 |
|---|---|
| `AuthInterceptor.java` | `X-User-Id`ヘッダを検証する「関所」。Controllerに届く前に必ず通る |
| `AuthContext.java` | 検証済みのログインユーザー情報を、そのリクエストの間だけ保持する入れ物 |
| `CurrentUser.java` | ログインユーザー情報そのもの（id・名前・role） |
| `WebConfig.java` | `AuthInterceptor`をどのURLに適用するか、CORS（frontendからのアクセス許可）の設定 |
| `exception/UnauthorizedException.java` | 401（未認証）を表す例外 |
| `exception/ForbiddenException.java` | 403（権限不足）を表す例外 |
| `exception/NotFoundException.java` | 404（データが見つからない）を表す例外 |
| `exception/BusinessException.java` | 400（業務ルール違反、定員超過など）を表す例外 |
| `exception/ErrorResponse.java` | エラー発生時にJSONとして返す形の定義 |
| `exception/GlobalExceptionHandler.java` | 上記の例外を全部キャッチし、統一されたJSON形式に変換する係 |

#### `resources/` — 設定ファイル・DB関連

| ファイル | まとめられている内容 |
|---|---|
| `application.yml` | DBの接続先など、アプリ全体の設定（パスワードなどの秘密情報は書かない） |
| `application-local.yml` | 実際のDBパスワード（**Gitには含まれない、各自のPCにだけ存在**） |
| `db/schema.sql` | テーブルを作成するDDL（CREATE TABLE文） |
| `db/seed.sql` | 初期データ（固定ユーザー2件、サンプルイベント4件） |

### 2.2 frontend（`frontend/src/app/`）

Angularでは、1つの画面・機能につき`.ts`（データと動き）・`.html`（画面の構造）・`.css`（見た目）の3点セットで作る。

#### `core/` — API通信など、画面をまたいで共通で使うもの

| ファイル | まとめられている内容 |
|---|---|
| `event-api.ts` | backendの`/api/events`系APIを呼び出す窓口。データの型（`EventSummary`/`EventDetail`）もここで定義 |
| `dummy-auth-interceptor.ts` | 送信する全リクエストに`X-User-Id`ヘッダを自動で付ける仕組み（ログイン画面ができるまでの暫定対応） |

#### `events/` — イベントに関する画面

| フォルダ | まとめられている内容 |
|---|---|
| `event-list/` | イベント一覧画面（`/events`）。`.ts`=一覧取得のロジック、`.html`=表の構造、`.css`=バッジ等の装飾 |
| `event-detail/` | イベント詳細画面（`/events/:id`）。`.ts`=詳細取得のロジック、`.html`=詳細表示の構造、`.css`=装飾 |

#### ルート直下（`src/app/`）— アプリ全体の骨組み

| ファイル | まとめられている内容 |
|---|---|
| `main.ts` | ブラウザが最初に実行するファイル。アプリを起動する |
| `app.ts` / `app.html` / `app.css` | 一番外側の部品。共通ナビ＋`router-outlet`（画面の差し込み口） |
| `app.config.ts` | HttpClient・Routerなど、アプリ全体に効く設定をまとめる場所 |
| `app.routes.ts` | URL（`/events`等）とコンポーネントの対応表 |
| `app.spec.ts` | `app.ts`のテストコード |

#### `src/`直下（`app/`の外）

| ファイル | まとめられている内容 |
|---|---|
| `index.html` | ブラウザが最初に読み込むHTML（中身は`<app-root>`だけ） |
| `styles.css` | アプリ全体に効くグローバルスタイル（現時点では未使用） |

### 2.3 リポジトリ全体のルート

| フォルダ/ファイル | まとめられている内容 |
|---|---|
| `docs/` | 設計書（要件定義書・API設計書・テーブル定義書等）とWBS |
| `docs/design/` | フェーズA（要件・設計）の正式な成果物 |
| `backend/` | バックエンド（Spring Boot）のプロジェクト一式 |
| `frontend/` | フロントエンド（Angular）のプロジェクト一式 |
| `.github/` | Issue・PRのテンプレート |
| `README.md` | セットアップ手順 |
| `.gitignore` | Gitで管理しないファイルの一覧 |
