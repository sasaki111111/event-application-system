# 13-02 機能別処理フロー

[13_システム動作・実装対応チェックリスト.md](13_システム動作・実装対応チェックリスト.md)の補助資料。主要な機能について「利用者の操作→画面→API→Controller→Service→Repository→DB→応答→画面」を、実際のコードにもとづいて追跡する。

**ファイル名の記載方針**：バックエンド（Java）はクラス名とファイル名が一致するため「`UserController.java`の`login()`」のように示す。フロントエンド（Angular）はファイル名（例：`event-list.ts`）とクラス名（例：`EventList`）が異なるため、各フローで最初に登場する箇所で「`event-list.ts`（`EventList`）」のように併記し、以降はファイル名で示す。

処理の順序・条件分岐の設計は`docs/30_詳細設計/32_処理詳細設計書.md`3章・4章、業務ルール（R-xx）は同5章、エラーID（E-x-xxx）は`docs/30_詳細設計/33_共通詳細設計書.md`3章を参照。

## フロー1：ログイン・利用者登録（F-010・F-011）

```
① 利用者が /login を開く
  ↓ login/login.ts（Login）が表示される（SC-010。ガードなし）
② メールアドレスとパスワードを入力し「ログイン」を押す
  ↓ login.ts の login()：メールアドレスは前後の空白を除去、パスワードはそのまま
    どちらかが未入力ならAPIを呼ばずにエラーを表示して終了
③ core/login-api.ts（LoginApiService）の login(email, password) → POST /api/login
  ↓ auth-header-interceptor.ts：未ログインのためX-User-Idを付けない
④ RateLimitInterceptor.java（書き込み系として回数を数える）
  ↓ AuthInterceptor.java は /api/login を対象外（WebConfig.java の excludePathPatterns）
⑤ UserController.java の login()：@Valid LoginRequest（@NotBlank @Email、パスワードは @NotBlank @Size(max=72)）
⑥ UserService.java の login(email, password)
   a. normalizeEmail（前後の空白除去＋小文字化）→ UserRepository.findByEmail
   b. 利用者が無い／退会済み／password_hashがNULL／PasswordEncoder.matches が偽
      → UnauthorizedException（401、E-A-006。理由によらず同じメッセージ）
   c. 成功 → 「ログイン成功 userId=…」をINFOログに出力
⑦ UserResponse{userId, name, email, roleCode, roleName, anonymizedAt} を200で返す
   （パスワード・ハッシュ値は含めない。roleNameはCodeNameResolverがrolesから取得）
⑧ login.ts の subscribe
   成功：LoginUserStore.login(userId, roleCode) → signalとlocalStorageに保存
         roleCode が管理者（2）なら /admin/dashboard、それ以外は /events へ遷移
   失敗：サーバーのメッセージをそのまま表示（言い換えない）
```

利用者登録（F-011）は③以降が`LoginApiService.register(name, email, password)`→`POST /api/users`→`UserController.register()`（`@Valid UserRegisterRequest`）→`UserService.register()`に替わる。`UserService.register()`はメールアドレスを正規化して`existsByEmail`で重複を確認し（重複時は存在を断定しない文言でE-B-015）、パスワードをBCryptでハッシュ化して`role_code=1`（一般利用者）で登録する。成功時は`login.ts`がそのまま`LoginUserStore.login()`を呼んでログイン状態にし、`/events`へ遷移する。`POST /api/users`は`AuthInterceptor`の中でメソッドとパスを判定して認証を省略している（`GET /api/users`は管理者専用のため対象外）。

ログイン後の全リクエストでは、`authHeaderInterceptor`が`LoginUserStore.currentUserId()`を`X-User-Id`ヘッダに付け、`AuthInterceptor`がその値で`UserRepository.findById()`を呼んで利用者を特定し、`AuthContext`に設定する。以降のフローの`requireAdmin()`は`AuthContext`のメソッドである。

## フロー2：イベント申込（キャンセル待ちを含む）（F-022）

```
① 一般利用者がイベント一覧（SC-020）を開いてカードを展開する、またはイベント詳細（SC-022）を開く
  ↓ events/event-list/event-list.ts（EventList）の toggleExpand() または events/event-detail/event-detail.ts（EventDetail）の ngOnInit()
    → core/event-api.ts（EventApiService）の detail(id) → GET /api/events/{id}
② 参加区分（設定がある場合）・アンケート回答（設定がある場合）を入力し「申し込む」を押す
  ↓ event-list.ts の apply(eventId) または event-detail.ts の apply()
③ core/application-api.ts（ApplicationApiService）の apply(eventId, ticketTypeId?, extraAnswer?)
  ↓ POST /api/applications { eventId, ticketTypeId, extraAnswer }
④ ApplicationController.java の apply()
   requireGeneral()：管理者なら ForbiddenException（403、E-A-005）
   validate(request)：手動のBean Validation（eventIdの必須、アンケート回答の文字数・見えない文字）
⑤ ApplicationService.java の apply(userId, eventId, ticketTypeId, extraAnswer)（@Transactional）
   a. EventRepository.findByIdAndDeletedAtIsNull（無ければ404、E-B-001）
   b. event.isOpen(now) が偽 → BusinessException「申込受付は終了しました」（400、R-01・E-B-002）
   c. existsByUser_IdAndEvent_IdAndStatusIn(受付済・キャンセル待ち) が真
      → BusinessException「すでに申し込み済みです」（400、R-03・E-B-003）
   d. resolveTicketType()
      区分の無いイベント：ticketTypeId の指定があれば404（E-B-005）、無ければ区分なし
      区分のあるイベント：未指定なら400「区分を選択してください」（C-03・E-B-004）
                          TicketTypeRepository.findByIdAndEvent_IdForUpdate で区分行を悲観ロック（無ければ404）
      区分の無いイベントは EventRepository.findByIdForUpdate でイベント行を悲観ロック
   e. 受付済数 < 定員（区分があれば区分単位）なら 受付済（1）、そうでなければ キャンセル待ち（2）（R-02）
   f. Application を保存（applied_at は現在時刻）。申込の成功はログに出さない
⑥ INSERT INTO applications(...)
⑦ ApplicationResponse{id, eventId, ticketTypeId, userId, statusCode, statusName, appliedAt} を201で返す
⑧ event-list.ts／event-detail.ts の subscribe
   router.navigate(['/events', eventId, 'done'], { state: { application } })
⑨ events/apply-done/apply-done.ts（ApplyDone、SC-023）が navigation state から申込結果を読み、
   statusName を表示する。statusCode がキャンセル待ちの場合は案内文を追加で表示する
```

**排他制御**：⑤dで取得した悲観ロックはトランザクションの終了まで保持されるため、同じイベント（区分）への同時申込は1件ずつ処理される（`docs/30_詳細設計/32_処理詳細設計書.md`7章）。`ApiIntegrationTest#o01_同時に申し込んでも定員を超えて受付済にならない`（ST-NF-N01）で、定員1のイベントに2件の申込を同時に送っても受付済が1件だけになることを確認している。

## フロー3：申込キャンセルと自動繰り上げ（F-023）

```
① 利用者がマイページ（SC-030）を開く
  ↓ my-applications/my-applications.ts（MyApplications）の ngOnInit → loadApplications() → GET /api/my/applications
② 対象の申込で「キャンセル」を押す → confirm() で確認
  ↓ my-applications.ts の cancel(application)
③ ApplicationApiService の cancel(id) → DELETE /api/applications/{id}
④ ApplicationController.java の cancel()：利用者IDは AuthContext から取得（リクエストには含めない）
⑤ ApplicationService.java の cancel(userId, applicationId)（@Transactional）
   a. ApplicationRepository.findById（無ければ404、E-B-009）
   b. 申込の利用者が本人でない → ForbiddenException（403、E-A-003）
   c. 状況が受付済・キャンセル待ちのいずれか、かつ開催前でなければ BusinessException「取消できません」（400、R-04・E-B-010）
   d. 元の状況が受付済だったかを記憶 → application.cancel()（キャンセル済＝9）
   e. 元が受付済の場合のみ：
      区分があれば TicketTypeRepository.findByIdForUpdate、無ければ EventRepository.findByIdForUpdate で悲観ロック
      → 同じ区分（区分が無ければ同じイベントの区分なしの申込）で最も申込日時が古いキャンセル待ちを1件取得
      → あれば application.promote()（受付済＝1、R-05）
⑥ UPDATE applications SET status_code = 9 …（繰り上げがあれば別の1行を status_code = 1 に更新）
⑦ 204を返す。キャンセル・繰り上げの成功はログに出さない（applicationsの行と updated_at で確認できるため）
⑧ my-applications.ts の subscribe → loadApplications() で一覧を取り直す
   繰り上げられた利用者には、次にマイページを開いたときに AP-031 で反映される（通知の仕組みは無い）
```

キャンセル待ちの順位（`waitlistRank`）は、`ApplicationService.calculateWaitlistRank()`が、自分より申込日時が古い同じ対象（区分単位／イベント単位）のキャンセル待ちの件数＋1を都度計算する。

## フロー4：イベント登録・編集（参加区分を含む）（F-120）

```
① 管理者がイベント管理（SC-120）で「＋ 新規登録」、またはイベント名を押す
  ↓ admin/admin-event-list/admin-event-list.html の routerLink → /admin/events/new または /admin/events/:id/edit
② admin/admin-event-form/admin-event-form.ts（AdminEventForm、SC-121）の ngOnInit()
   編集：EventApiService.detail(id) で既存の値を取得して form.patchValue、区分をFormArrayに追加、
         読み込んだ時点の区分の内容（loadedTicketTypes）を記憶
   新規：複製元（navigation state の duplicateFrom）があれば、開催日時・申込締切以外を複写
③ 管理者が入力する（参加区分は「＋ 区分を追加」で行を追加・削除）
④ 「保存」を押す → submit()
   form.invalid（Validators.required・min(1)）なら markAllAsTouched() して送信しない
   capacity：区分が1件以上なら区分の定員合計、無ければ入力値
   ticketTypes：編集で区分が読み込み時から変わっていなければ送らない（undefined）
⑤ 新規：EventApiService.create(request) → POST /api/events
   編集：EventApiService.update(id, request) → PUT /api/events/{id}
⑥ EventController.java の create()／update()
   authContext.requireAdmin()（一般利用者は403、E-A-002）→ validate(request)（@ValidEventDatesを含む）
⑦ EventService.java の create()／update()（@Transactional）
   新規：resolveCapacity → new Event(...) → EventRepository.save
   編集：findByIdOrThrow（無ければ404、E-B-001）→ resolveCapacity → event.applyChanges(...)
   resolveCapacity：capacity の指定 → 区分の定員合計 →（更新で区分の指定なし）既存区分の合計 の順に決め、
                    どれも無ければ400「定員を入力してください」（R-11・E-B-006）
   saveTicketTypes(event, request.ticketTypes())
     null（指定なし）：既存の区分を維持し、区分があれば capacity を既存の合計に同期
     指定あり：
       受付済・キャンセル待ちの申込が残っている → 400「区分に申込があるため変更できません」（R-09・E-B-007）
       既存の区分を全件削除して flush（キャンセル済の申込が参照していれば外部キー違反 → 400、E-B-017）
       空の配列 → 区分なしで終了
       区分名の重複 → 400「区分名が重複しています」（R-10・E-B-008）
       新しい区分を保存し、capacity を区分の定員合計に同期
   「イベント登録完了／更新完了 eventId=… 実行者userId=…」をINFOログに出力
⑧ events に INSERT／UPDATE、ticket_types に DELETE→INSERT（全置換）
⑨ EventDetailResponse を返す（登録は201、更新は200）
⑩ admin-event-form.ts の subscribe → /admin/events（SC-120）へ遷移
   エラー：400＋errors[] は項目ごとに表示、403・404は固定のメッセージ、それ以外はサーバーのメッセージ
```

区分を変えずに編集した場合に区分を送らないのは、送ると区分の全置換として扱われ、有効な申込があるイベントでは区分以外の項目も保存できなくなるためである（`docs/30_詳細設計/31_API詳細設計書.md`AP-121「参加区分の扱い」）。

```

```
