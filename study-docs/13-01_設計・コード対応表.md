## 3. 入力チェックの層別整理

チェックの実施場所と順序は`docs/20_基本設計/24_方式設計書.md`4章、個々のチェックとエラーIDは`docs/30_詳細設計/33_共通詳細設計書.md`2章・3.1に定める。

| 対象 | 内容 | 画面 | サーバー（DTOのアノテーション） | サーバー（Service） | DB制約 |
|---|---|---|---|---|---|
| メールアドレス（ログイン） | 必須・形式 | 未入力ならAPIを呼ばない（`login.ts`） | `LoginRequest`：`@NotBlank @Email`（E-V-001） | `normalizeEmail`で小文字化して検索 | - |
| パスワード（ログイン） | 必須 | 未入力ならAPIを呼ばない | `@NotBlank @Size(max=72)`（E-V-024） | `PasswordEncoder#matches`（R-22） | - |
| 名前（利用者登録・管理者登録） | 必須・100文字以内・見えない文字を含まない | - | `UserRegisterRequest`：`@NotBlank @Size(max=100) @Pattern`（E-V-002） | - | `VARCHAR(100) NOT NULL` |
| メールアドレス（登録） | 必須・形式・255文字以内・重複不可 | - | `@NotBlank @Email @Size(max=255)`（E-V-003）。前後の空白はDTOの生成時に除去 | `existsByEmail`（R-15・E-B-015） | `uk_users_email` |
| パスワード（登録・変更） | 8〜72文字、英字と数字を含む、半角の英字・数字・記号のみ | パスワード変更は未入力・確認用との不一致をAPIを呼ばずに表示 | `@NotBlank @Size(min=8,max=72) @Pattern(PASSWORD)`（E-V-025・E-V-027） | パスワード変更は現在のパスワードを照合（R-23・E-B-023） | - |
| イベント名・場所 | 必須・100文字以内・見えない文字を含まない | `Validators.required` | `EventUpsertRequest`：`@NotBlank @Size(max=100) @Pattern`（E-V-010・E-V-012） | - | `VARCHAR(100) NOT NULL` |
| 開催日時 | 必須・未来の日時 | `Validators.required` | `@NotNull @Future`（E-V-011） | - | `DATETIME NOT NULL` |
| 申込締切 | 必須・開催日時より前 | `Validators.required` | `@NotNull`（E-V-014）、クラス全体に`@ValidEventDates`（C-01・E-V-021） | - | 無し（アプリ側で担保） |
| 定員 | 1以上。区分が無い場合のみ必須 | `Validators.required, Validators.min(1)`（区分がある場合は区分の合計を表示のみ） | `@Min(1)`（E-V-013）。`@NotNull`は付けない | `resolveCapacity`（R-11・E-B-006） | `CHECK (capacity >= 1)` |
| 画像URL | 500文字以内・http/httpsで始まる | - | `@Size(max=500) @Pattern(HTTP_URL)`（E-V-017） | - | `VARCHAR(500)` |
| 参加区分名 | 必須・50文字以内・同一イベント内で重複不可 | `Validators.required` | `TicketTypeRequest`：`@NotBlank @Size(max=50) @Pattern`（E-V-019） | `saveTicketTypes`の重複チェック（R-10・E-B-008） | `uk_ticket_types_event_name` |
| 参加区分の定員 | 必須・1以上 | `Validators.required, Validators.min(1)` | `@NotNull @Min(1)`（E-V-020） | - | `CHECK (capacity >= 1)` |
| 申込の参加区分 | 区分があるイベントでは必須 | - | 単項目チェックなし | `resolveTicketType`（C-03・E-B-004、存在しない区分はE-B-005） | `ticket_type_id`はNULL可 |
| アンケート回答 | 500文字以内・見えない文字を含まない | - | `ApplicationCreateRequest`：`@Size(max=500) @Pattern`（E-V-006） | - | `VARCHAR(500)` |
| コメント本文 | 必須・500文字以内・見えない文字を含まない | 空白のみなら送信しない | `EventCommentCreateRequest`：`@NotBlank @Size(max=500) @Pattern`（E-V-008） | 返信先が同じイベントのコメントか（C-06・E-B-016） | `VARCHAR(500) NOT NULL` |
| 定員（申込時） | 超過時はキャンセル待ち（拒否しない） | - | - | `apply`で受付済数と定員を比較（R-02） | 都度集計（集計カラム無し） |
| 定義されていない項目 | 無視する | - | Jacksonの既定の動作 | - | - |

**二重の防止**：メールアドレス・参加区分名・お気に入りの重複は、Serviceでの事前チェックとDBのUNIQUE制約の両方で防ぐ。二重申込は、キャンセル後の再申込を許すため`applications(user_id, event_id)`にUNIQUE制約を設けず、Serviceのチェック（R-03）と悲観ロックによる直列化で防いでいる。

## 4. エラー処理の流れ

| エラーの種類 | 検知する場所 | 例外・HTTPステータス | 応答を作る場所 | 画面での表示 |
|---|---|---|---|---|
| 認証エラー（未ログイン・退会済み） | `AuthInterceptor#preHandle` | `UnauthorizedException`→401（E-A-001） | `GlobalExceptionHandler#handleUnauthorized` | `httpErrorInterceptor`がログイン状態を解除してSC-010へ遷移 |
| ログイン失敗 | `UserService#login` | `UnauthorizedException`→401（E-A-006） | 同上 | SC-010にサーバーのメッセージを表示（自動遷移の対象外） |
| 権限エラー | `AuthContext#requireAdmin`、`ApplicationController#requireGeneral`、Serviceの本人確認 | `ForbiddenException`→403 | `#handleForbidden` | その場にメッセージを表示（遷移しない） |
| データ未検出 | 各Serviceの`orElseThrow` | `NotFoundException`→404 | `#handleNotFound` | メッセージを表示 |
| 業務ルール違反 | 各Service | `BusinessException`→400 | `#handleBusiness` | メッセージを表示 |
| 入力エラー | `@Valid`、またはControllerの手動`validate()` | `MethodArgumentNotValidException`／`ConstraintViolationException`→400（`errors[]`付き） | `#handleValidation`／`#handleConstraintViolation` | 項目ごとに表示（`admin-event-form.ts`、`login.ts`、`admin-user-list.ts`、`password-change.ts`） |
| リクエスト形式エラー | Spring MVC | 不正なJSON・型の不一致→400（E-V-022・E-V-023）、存在しないURL→404、未対応のメソッド→405、JSON以外の本文→415（E-V-028〜E-V-030、ログに出さない） | `#handleMalformedRequest`ほか | メッセージを表示 |
| リクエスト過多 | `RateLimitInterceptor#preHandle` | 429（E-R-001） | `RateLimitInterceptor`が直接書き込む（`GlobalExceptionHandler`を経由しない） | メッセージを表示 |
| 想定外の例外 | どこでも | `Exception`→500（E-S-001） | `#handleUnexpected`（スタックトレースはログのみ） | 固定のメッセージを表示 |
| 通信エラー | Angularの`HttpClient` | status 0 | `httpErrorInterceptor`が共通のメッセージに置き換える | 「サーバーに接続できません。…」 |

認可を入力チェックより先に行う（`docs/20_基本設計/23_API基本設計書.md`2.5）ため、管理者専用の登録・更新API（AP-120・AP-121・AP-145）と一般利用者専用のAP-030は`@Valid`を使わず、Controllerの中で認可チェックの後に`Validator#validate`を呼ぶ。それ以外のAPIは`@Valid`を使う。

## 5. 設計からコードまでの追跡例

```
業務ルール（docs/10_要件定義/10_要件定義書.md 7章）
  「定員に達している場合はエラーにせず、キャンセル待ちとして登録する」
  ↓
業務ルールの判定方法（docs/30_詳細設計/32_処理詳細設計書.md 5章 R-02）
  acceptedCount < capacity
  ↓
機能：F-022 イベント申込 ／ API：AP-030 POST /api/applications
  ↓
Controller：ApplicationController#apply（requireGeneral → validate）
  ↓
Service：ApplicationService#apply
  int status = acceptedCount < capacity ? ApplicationStatus.ACCEPTED : ApplicationStatus.WAITLISTED;
  ↓
Entity：Application（status＝申込状況コード 1または2）
  ↓
DB：applications.status_code（SMALLINT、application_statusesへの外部キー）
```

同様に、「同一イベント内で参加区分名を重複させない」は、10_要件定義書7章 → 32_処理詳細設計書 R-10 → `EventService#saveTicketTypes`の重複チェック → `ticket_types`の`uk_ticket_types_event_name`、「最後の管理者は降格できない」は、32_処理詳細設計書 R-17 → `UserService#demote`の`countByRoleCode(RoleCode.ADMIN) <= 1`、という線で追跡できる。
